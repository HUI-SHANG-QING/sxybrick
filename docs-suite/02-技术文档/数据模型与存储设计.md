# 数据模型与存储设计

## 1. 存储选型

- **本地**：IndexedDB，通过 Dexie 4 封装。schema 当前版本 v16，16+ 张表。
- **为什么不用 localStorage**：localStorage 只能存字符串、容量小（~5MB）、不支持索引与事务；IndexedDB 能存结构化对象、建索引、跨表事务，适合成百上千张卡。
- **跨设备**：不依赖云数据库，用"字段级合并 + 墓碑"把同步做成纯数据问题。

## 2. 核心表（逻辑）

| 表 | 存什么 | 关键字段 |
|---|---|---|
| cards | 知识卡片 | front/back/subject/tags/level/dueAt/stability/difficulty/marked/source |
| reviews | 每次复习记录 | cardId/rating/ts/elapsed |
| plans / dailyPlans | 学习计划/每日规划 | title/content/status/tasks |
| docs | AI 文档 | title/content/type/tags |
| docFiles / docTexts | 资料库文件与其解析文字 | name/kind/pageCount/text |
| graphEdges | 知识图谱边 | from/to/fromCardId/toCardId/label/kind |
| memos | 四象限备忘 | text/important/urgent |
| embeddings | 向量索引 | sourceId/vector/modelSig |
| exams | 模考记录 | title/subject/questions[]/score/total |
| words / wordGroups | 英语单词本 | word/meaning/tags/kind(生词/熟词) |
| 墓碑(tombstone) | 删除标记 | id/deletedAt/rev |

## 3. 索引设计（真实）

- 每张表的高频查询字段都建了索引：cards 按 dueAt、subject、tags；reviews 按 cardId、ts。
- 全库查询无"翻全表"：AI 检索向量用批量 anyOf，避免"查一张跑一趟"的 N+1。

## 4. 关键数据结构设计点

- **卡片状态机**：一张卡的 S/D/dueAt 由 fsrs 计算，不允许界面直接改 dueAt（防止绕过调度逻辑）。
- **删除是软删+墓碑**：删一张卡，牵连的复习记录、分组链接、图谱边、向量块全部进**同一个事务**写墓碑——中途断电也不会留下"删了一半"的卡；墓碑会同步到其他设备，保证"这边删了，那边也删掉"。
- **字段级时间戳**：每个可编辑字段记 lastModified，两台设备分别改一张卡的正面和背面，合并时两边都保留（不会互相覆盖）。

## 5. 与单词模块的数据协同

- 单词分"生词/熟词/词组/长难句"：新加进来默认是生词；标为熟词后在"单词"默认列表里隐藏、只在"熟词"分类出现。
- 单词复习与卡片复习共用同一套 FSRS 调度，进度独立但算法一致。

## 6. 一致性风险与对策（已在代码中处理）

| 风险 | 对策 |
|---|---|
| 两端同时改同字段 | LWW（最后写入赢），平局用确定性 tiebreaker（消息数多者赢，再平保持本地），不看同步时序 |
| 删了又被推回来 | 墓碑传播，向量块也墓碑 |
| 向量模型降级 | 落降级签名，模型恢复自动重建 |
| 空数据/脏数据 | dueAt=0 退回 createdAt；空库返回空结构不报错 |
