# 系统架构设计

## 总体架构（三层）

```
┌─────────────────────────────────────────────────────────┐
│  表现层  Vue 3 SPA（48 个视图）                            │
│  router → views/ → components/ → composables/ → stores/  │
│  ECharts 可视化 · Element Plus · KaTeX 公式               │
├─────────────────────────────────────────────────────────┤
│  智能层  AI Agent 子系统（src/agent/）                     │
│  orchestrator(ReAct) → tools(40+工具) → agents(10个智能体) │
│  retrieval(向量RAG) · embedding · blackboard(多Agent黑板)   │
│  memory(长期记忆) · proactive(主动建议) · local-answer(兜底)│
├─────────────────────────────────────────────────────────┤
│  数据层  Dexie / IndexedDB（16+ 张表，纯本地）             │
│  repo.js / repo-core.js / word-repo.js / docs-lib.js      │
│  fsrs.js(记忆算法) · algorithms/(图谱/错题/预测)           │
│  sync.js / sync-manifest.js(双时间戳合并+墓碑)             │
└─────────────────────────────────────────────────────────┘
        ↑ AI 调用（用户自备 Key）        ↑ 跨设备
   远程 LLM / Embedding API          sync-hub/ 局域网中枢
```

**关键设计取舍**：这是一个**纯前端、无应用服务器**的 PWA。所有业务数据存浏览器 IndexedDB；唯一的"后端"是用户自带的 LLM/Embedding API，以及一个可选的 Node 局域网同步中枢。这样做的代价是没有多租户账号体系，收益是：零服务器成本、离线可用、数据完全归用户。

## 分层职责

### 1. 表现层（src/views, components, stores）
- **路由** `src/router.js`：48 个视图按功能域组织（卡片/复习/单词/规划/图谱/费曼/考试/资料库/同步等）。
- **状态** Pinia stores 管理界面状态；跨页共享数据尽量走 repo 层（IndexedDB 是唯一数据源），不在组件里重复造状态。
- **可视化** ECharts（趋势/雷达/热力/词云/知识图谱力导向）。
- **工程约束**：所有界面文案走 i18n（`src/i18n/`），有自动化闸门 `check-view-i18n.mjs` 禁止硬编码中文。

### 2. 智能层（src/agent）
- **编排器 orchestrator + pipeline**：ReAct 循环（思考→选工具→执行→观察→再思考）。
- **工具注册表 registry.js**：40+ 个工具（查统计/搜卡/建卡/出题/语义检索/读写黑板…），每个工具声明 readsData/writesData，开闭原则加工具。
- **智能体 agents/**：10 个角色，各有 system prompt，通过 `delegate_to_agent` 互相委托。
- **RAG** retrieval.js + embedding.js：远程向量模型优先，失败自动降级本地；混合检索 = 语义分 ×0.65 + 关键词分。
- **多 Agent 黑板 blackboard.js**：协作模式下各 Agent 写 finding/artifact，其他 Agent 可读。
- **兜底** local-answer.js：工具已拿到数据但"总结"那步 LLM 失败时，用确定性模板把结构化数据渲染成 Markdown，不丢数据。

### 3. 数据层（src/repo*.js, db.js, algorithms/）
- **db.js**：Dexie schema（v16，16+ 表），每处查询都有索引。
- **repo.js / repo-core.js**：卡片/复习/计划/文档的 CRUD，删除走"事务级软删+墓碑"。
- **fsrs.js**：FSRS-4.5 核心调度（19 权重、记忆方程、梯度训练、校准回测）。
- **algorithms/**：graphAuto（自动建图）、prereq（前置回溯）、mistakeAttribution（TF-IDF 错题聚类）、forecast（到期洪峰预测）。
- **sync.js / sync-manifest.js**：双时间戳（字段级 lastModified）LWW 合并 + 墓碑传播。

## 关键数据流

1. **复习一次**：Review 视图 → repo.reviewCard(卡id, 评分) → fsrs.schedule() 算出下次到期 → 写 reviews 表 + 更新卡的 dueAt/stability → dbEvents 通知 → UI 刷新。
2. **AI 回答一次问题**：AIAssistant → orchestrator ReAct → 需要资料时调 semantic_search → retrieval 先向量检索卡片/文档 → 拼进上下文 → 调 LLM → 流式渲染。
3. **跨设备同步**：任意设备改数据 → sync.js 生成变更 → 经 hub 或 JSON 包 → 对端 sync-manifest.merge 按字段时间戳合并 → 墓碑保证删除传播。

## 为什么这样分层

- **UI 不碰 SQL**：组件只调 repo.js 的命名函数，不直接写 Dexie 查询——这样换存储（比如以后加后端）只动 repo 层。
- **算法与 UI 隔离**：fsrs/retrieval/图谱都是纯函数、零 DOM 依赖，能在 Node 里直接 `node --test` 单测（这是 1079 个测试的基础）。
- **AI 与数据隔离**：Agent 只能通过"工具"读数据，不能直接改库；加新工具不影响编排器。
