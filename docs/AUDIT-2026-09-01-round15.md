### P1（3 项，全部修复）

**P1-1 `createDailyPlan` 覆盖重建无事务 → 当天计划清空但新计划未建成的半残态**
`repo.js:582`：先逐条级联删旧计划（删任务+删行+写墓碑）再新建计划，全程无事务。任一步失败（配额/断电/异常）即产生「今天没有计划」的不可恢复状态。
修复：解析（含动态 import）移到事务外，覆盖重建 + 新建计划 + bulkPut 任务整体包进 `db.transaction('rw', dailyPlans, dailyTasks, tombstones)`。

**P1-2 删除级联不完整 → 对端残留孤儿行/幽灵边/幽灵向量，随 idOnly 增量反复回传**
- `deleteCard`（repo.js:276）：删图边不写 graphEdge 墓碑（对端旧边按 updatedAt 合并被推回 → 幽灵边复活）；不删 embeddings（本端 RAG 检索到已删卡的幽灵向量）。
- `deleteWordCard`（word-repo.js:158）：删 wordReviews 不写 wordReview 墓碑（对端 idOnly 幂等保留 → 孤儿复习记录常驻 + 统计污染）。
- `sync.js` step4 卡片墓碑应用：只级联删 reviews，不级联远端 embeddings/graphEdges。
修复：deleteCard 事务内写 graphEdge 墓碑（删除前取边列表）+ 删 embeddings（sourceId 索引 + sourceType='card'）；deleteWordCard 事务内对 wordReviews 写墓碑；sync.js step4 兜底清理远端 embeddings/graphEdges。

**P1-3 `reviewWord` template 分支 bump updatedAt → 浏览范文用旧副本覆盖对端编辑**
`word-repo.js:37`：`put({ ...plain(card), reviewedAt: t, updatedAt: t })`——与文件内「复习不 bump updatedAt（与 repo.review 一致）」注释自相矛盾。浏览范文是复习动作，bump 会让跨设备同步覆盖对端对范文的编辑。
修复：只写 `reviewedAt`，去掉 `updatedAt`。回归：template 测试断言 updatedAt 不变。

### P2（8 项，全部修复）

**P2-1 FSRS 蒙对 S 虚高（算法）**：srs.js 原实现蒙对仅 `intervalDays × 0.6`，但 `fsrs.schedule` 仍按 good（grade=3）`stabilityAfterRecall` 完整提升 S（单步≈2.6×）→ 蒙对卡与真记住同速增长，远期间隔系统性放大；与 SM-2「蒙对不升级、降 ease」语义不一致。
修复：蒙对（rating=2 + guessed）时以 rating=1（hard）推进 FSRS 状态——hard 档 S 增长小、D 增加，语义对齐；移除 0.6 乘子。回归：蒙对 S ≤ 真记住 S。

**P2-2 `getForgetRisk` dueAt 缺失 → 逾期 2 万年霸榜（算法）**：`dueIn = (c.dueAt ?? 0) - nowTs`，同步/导入旧卡 dueAt=0 → overdueDays≈20700 → 恒过 0.35 阈值霸榜预警与自动计划。
修复：`dueAt` 非有限正数直接跳过（无排期不算逾期）。

**P2-3 `getSubjectDiagnosis` 无视 noData → 零复习科目误判「学得最差」（算法）**：`masteryMap.get(subject) || 0` 把零复习科目当掌握度 0，建议「先回看基础概念、放慢加卡速度」，且 subjRank 排最前。
修复：消费 mastery 的 `noData` 标记，无数据科目不给掌握度建议。

**P2-4 idRemap 数组/嵌套引用字段漏网（数据协同）**：`CARD_REF_FIELDS` 仅标量（cardId/fromCardId/toCardId/sourceId）；notes.linkedCardIds、plans.linkedCardIds（数组）、analysisSessions.cardIds（JSON 串）、exams.questions[].cardId（嵌套）在去重跳过后成孤儿引用。
修复：新增 ARRAY_REF_FIELDS / JSON_REF_FIELDS / NESTED_REF_FIELDS 三组重定向。回归：8 类字段断言。

**P2-5 wordSyllabusMeta 增量永不上传（数据协同）**：行活跃时间戳 `loadedAt` 不在 LIVENESS_FIELDS → livenessTs=0 → 增量包每轮滤掉。
修复：LIVENESS_FIELDS 补 `loadedAt`。回归：livenessTs 识别。

**P2-6 清空水位死代码 → 隐私删除失效（隐私）**：`clearedBeforeKey`/`filterClearedRows` 定义后无调用点；wipeUserOps/wipePrivacy 直接 `clear()` 不写水位 → 下轮同步把 hub 历史行灌回，「撤销监控」失效。
修复：wipe 写 `localStorage.setItem(clearedBeforeKey(table), now)`；importBackup 合并入口按水位过滤入站行。回归：filterClearedRows 过滤语义。

**P2-7 graph-resolve 节点键 30 字截断 → 同前缀卡合并成单节点（图谱）**：节点键 = front 前 30 字，`TCP 三次握手详解（上/下）` 这类同前缀不同卡被 putNode 合并，关系错画。
修复：节点键 = cardId 优先（无 cardId 的资料型边退回应文本）；edges.from/to 同步改节点键；tree 布局回查 label 显示；bySubject 按 visibleEdges 统计。回归：graph-idspace 端点键断言适配。

**P2-8 5 处 delete+墓碑无事务 → 跨设备删除失效（业务）**：deleteDailyTask/deleteGraphEdge/deleteWeeklyReport/deleteExam/deletePrivacyRecord 均先 delete 再 put 墓碑，墓碑写失败 → 对端无墓碑把记录推回，删除永不生效。
修复：5 处统一 `db.transaction('rw', 表, tombstones, ...)`。

## 2. 交叉分析：可扩展方向 / 可优化点 / 需修复缺陷

### 可扩展功能（用户价值排序）
1. **搜索性能优化**（P3-10）：卡片/文档类先按标题索引粗筛，大字段截断匹配窗口，结果级缓存——万卡场景搜索卡顿的根因。
2. **AI 批量生成队列**：word-llm 单卡已通，缺批量排队/重试（round13 扩展方向遗留）。
3. **subject 数据值 key 化**（P3-3 round14）：需数据迁移层，列为设计改进项。

### 可优化点
- `listCards` 尾部 dueCount 全表重查（P3 业务层）——可复用已过滤数组。
- `createWordCard` 无长度上限——word/meaning 截断，防超大行拖慢列表。
- `reset.js` 清库不清 OPFS 原文件 + 清 deviceId（改变同步身份）——独立清理批次。

### 需修复缺陷（下一批候选）
- fsrs.trainWeights 训练起点（P3-5）、首复习失败 S（P3-6）、firstReviewedAt NaN（P3-7）。
- hub.js mergeRows 未传 `{ strip }`（round14 P3 遗留）——hub 副本 llmApiKey 被抹，设备本地不受影响。
- wordCheckins 跨时区 id（`c-${本地日期}`）——同日不同时区双条，需 UTC 归一（数据契约变更，谨慎）。
