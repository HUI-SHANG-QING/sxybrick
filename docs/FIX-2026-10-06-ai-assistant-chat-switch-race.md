## 一、`onTrace` 写入污染（我 round135 引入）

### 现象
AI 思考过程中，**思考内容与最终答案会写进「别人」的对话**，并被 `persist()` 存进库。

### 根因
侧栏会话列表在等待期间**没有任何 loading 保护**（只有发送按钮被 `:disabled="loading"` 挡住）：

```js
currentChat.value.messages.push({ role: 'assistant', content: '' });
replyIdx = currentChat.value.messages.length - 1;
const onTrace = (node) => {
  const ph = currentChat.value.messages[replyIdx];   // ← 读的是「当前」对话
```

用户在思考时点了另一条历史对话 → `currentChat.value` 被替换 → 后续 `onTrace`
按**下标**写进新对话 → 答案也写错 → `finally` 里的 `persist()` 把污染内容落库。

### 修法
**认对象，不认下标**：进入 `send()` 时捕获 `targetChat = currentChat.value`，
所有写入都指向它，并用 `isStale()` 判断"用户是否已切走"，切走即停止一切写入。

## 二、`revealBubble` 的「已切换会话」保护是**失效的**（既有）

它的注释与意图是对的：

```js
if (!m || m.content === text) return; // 已切换会话 / 已被替换 → 停
```

但**判据选错了**：切换后 `currentChat.value.messages[idx]` 指向的是**新对话的同下标消息**，
它**通常存在**、内容也不相同 ⇒ **判据不成立，循环继续写** ⇒ 照写不误；
循环结束后那句兜底 `if (m) m.content = text;` 还会**再写一次**。

⇒ 这是一处**注释声称已处理、实际没处理**的典型（与项目记忆里"注释与实现不符"的教训同源）。

**修法**：调用前先判 `isStale()`，切走就不走打字机（打字机是给**当前视图**看的，
对已切走的对话毫无意义），只把结果一次性落回原对话并保存。

## 三、`finally` 存错对话（既有，被上面两条触发）

`finally` 里固定 `await persist()`（存 `currentChat.value`）。用户切走后，
它存的是**新对话**——而新对话可能已经被污染，于是脏数据被持久化。

**修法**：切走时 `saveChat(targetChat)`（存回真正产生内容的那条对话）。

## 四、`thinkOpen` 下标跨对话错位（我 round135 引入）

思考展开态按**消息下标**存，而下标是**每个对话内部**的编号。
切换对话后沿用同一份 `thinkOpen`，展开态会张冠李戴。

**修法**：`selectChat` / `createNew` 时清空。

## 五、⚠️ 我"修一个又引出另一个"：删除的对话被写回来

第四项修完后**我自己发现的**：`removeChat` 删除正在进行的对话后，
`isStale()` 为 true → `saveChat(targetChat)` **把用户刚删的对话又写回去**，
等于**静默撤销了删除操作**。

> 这正是用户反复说的"每轮修复都会引出问题"——**我这一轮就亲身复现了一次**。
> 区别在于：它没跑到用户面前，被我在自查时逮住了。

**修法**：保存前先 `getChat(targetChat.id)` 确认它**还活着**，不在了就不写。
