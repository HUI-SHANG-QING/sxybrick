## 一、问题清单

### P3-1（值得修，2 行）：中枢**无条件信任客户端自报时钟**（x-client-time），坏设备可让己方数据在 LWW 合并中永远"最新"

**位置**：`sync-hub/hub.js:722-723`

```js
const clientTs = Number(req.headers['x-client-time']);
const clockSkew = Number.isFinite(clientTs) ? clientTs - Date.now() : 0;
```

**问题**：`x-client-time` 是客户端自报头，**无任何范围钳制**。正常用途是补偿真实时钟偏差（round30 P2-3 引入），但：
- 客户端误配（时钟坏了的旧设备/测试环境）或异常实现传 `0` → `skew = 0 - Date.now()` ≈ **负当前毫秒数** → incoming 所有时间戳减去这个巨数 → **该设备每条记录都变得"最新"**，LWW 合并（streakMeta/examMeta/schedMeta/卡片内容时间戳）**全面压过其他所有设备**；
- 反向传超大值 → 该设备永远"最旧"，修改被压制。
- 真实影响：一台时钟错乱的设备同步一次，会把错误的时间戳固化进 hub 并回灌全部设备（内容级 LWW 还能被后续正常设备翻回，但删除墓碑/元数据一旦被压过去，恢复靠手工）。

**修复建议**（约 5 分钟 + 测试）：
```js
const clientTs = Number(req.headers['x-client-time']);
// round89：钳制自报时钟——只接受 ±48h 内的合理偏差，超出视为恶意/坏时钟，忽略补偿
const rawSkew = Number.isFinite(clientTs) ? clientTs - Date.now() : 0;
const clockSkew = Math.abs(rawSkew) > 48 * 3600 * 1000 ? 0 : rawSkew;
```

### P3-2（备忘）：过期/重放的挑战按"口令猜测"惩罚——合法客户端的过期重试会被指数退避锁定

**位置**：`sync-hub/hub.js:487-489` + `auth-core.js:103-109`

**问题**：`authenticate()` 中挑战 `consume` 失败（不存在/已消费/**已过期**）一律走 `authLimiter.fail(ip)` → 指数退避锁定（1s→2s→…→15min）。挑战 TTL 60s，若客户端实现"重试原请求头"（网络抖动/慢速设备），重放过期挑战会触发与口令猜测同级的惩罚，把**合法用户锁出同步**。防重放是必要的，但"过期"≠"猜测"——语义上应区分。

**建议**：`consume` 返回三态（consumed / expired / notFound），仅 `notFound`（可能来自乱试）走 fail 退避；`expired`（合法重试的自然结果）只 401 不计入退避。低优先，取决于客户端是否重试原头（前端 sync.js 每次失败都会重新取挑战则无实际触发面）。

## 四、根因分析（交叉思考）

1. **信任边界**（P3-1）：同步协议把"时钟补偿"当成客户端善意能力——但凡是**客户端自报且参与合并判定的输入，都必须有界**。前端侧对删除墓碑做了 30 天未来钳制（round48，取向正确），中枢侧对 x-client-time 却没有同款钳制——**两端口径不一致**。
2. **惩罚语义**（P3-2）：把"协议自然失败"与"攻击行为"混用同一惩罚通道，是安全实现里常见的过度收紧；正确做法是**按失败原因分级**。

## 五、建议（影响 ÷ 成本）

1. **P3-1 时钟钳制**（5 分钟 + 2 条测试）——一行判断堵住单设备操纵全局合并判定的口子，成本极低；
2. P3-2 挑战三态（约半小时）——先确认前端 sync.js 失败是否重取挑战，若重取则记备忘不修。
