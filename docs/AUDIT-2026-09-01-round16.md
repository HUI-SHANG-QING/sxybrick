## 2. 新发现（本轮盲区扫描）

### P1（1 项）

**R16-1 `restoreFromTrash` 未清 `reviews` 墓碑 → 记忆卡删除恢复后，下一次同步复活自己的复习历史删除**

- **链路**：`deleteCard`（记忆卡）在 `repo.js` 删除 `reviews` 行时**未写 review 墓碑**（对照：round15 的 `deleteWordCard` 已补 `wordReview` 墓碑——同一漏洞单词侧修了、记忆卡侧漏了）。
- **后果**：卡片删除 → 复习行被物理删 → 但无墓碑，对端（或本地恢复前）的下次同步会把对端仍存在的 review 行**重新合并回来**（`mergeRows` 按 updatedAt 取新，本地已删的行在对端视角"不存在"，不会主动推空——真正致命的是反向：本地恢复卡片后，对端若曾同步过"无此卡"状态，其 review 行的删除语义没有墓碑载体，恢复后复习历史缺失且无法再同步回来）。
- **更直接的表现**：本地 `deleteCard` 后、`restoreFromTrash` 前，若触发一次同步，`exportRows` 导出的 `cards` 无此行，但 `reviews` 的行已被物理删且无墓碑——对端收到"cards 缺行 + reviews 无墓碑"的包，**不会删自己的 review 行**（无墓碑不触发），形成"卡没了、复习还在"的孤儿行；恢复卡后，孤儿 review 行与恢复的卡 id 不匹配，成为永久垃圾。
- **修复**：`deleteCard` 删 reviews 行时同步写 `tombstones`（kind:'review'，复用 round15 `deleteWordCard` 的墓碑写法）；`restoreFromTrash` 恢复卡片时 `tombstones.where('kind').equals('review').and(t=>t.refId===cardId).delete()` 清墓碑。补 1 条回归：删卡→同步→恢复→再同步，复习行不复活且不留孤儿。
- **定级 P1 理由**：数据协同层、跨设备、静默产生孤儿行，用户无感知但数据持续污染。

### P2（3 项）

**R16-2 `P2-7` 节点键改动打破 `Mindmap.vue` 导图生成**
- `graph-resolve.js` 的 `edgesToForest` 内部 `build()` 用 `e.from`/`e.to` 作为**节点显示名**构造森林（`name: e.from`）。P2-7 把 `resolveGraph` 输出的边 `from`/`to` 从 label 文本改为 cardId 后，`edgesToForest` 的节点 `name` 变成了 `card_xxxxx` 形式的内部 id，**导图树上显示的是卡片 id 而非知识点名称**。
- `KnowledgeGraph.vue` 已加 `nodeById` 适配（节点 id→label 映射），但 `Mindmap.vue:238-270` 直接消费 `resolveGraph` 的 edges 传给 `edgesToForest`，**未做同样的键→label 映射**。
- **验证**：`edgesToForest` 全库调用方仅 `Mindmap.vue` 一处（测试不计），波及面单一但致命——思维导图是核心视图，节点显示 id 属于"看起来能跑、实际全错"的静默回归。
- **修复**：`Mindmap.vue` 在调用 `edgesToForest` 前，用 `resolveGraph` 返回的 `nodes` 建 `id→label` 映射，把 edges 的 `from`/`to` 映射回 label 再传入；或让 `edgesToForest` 接受可选的 `labelMap` 参数。补 1 条回归：导图节点 name 为中文 label 而非 cardId。

**R16-3 `reviewWord` 信号链路半实现：`guessed`/`responseMs`/`retrievalStrength` 采集端存在、消费端断链**
- `WordReview.vue` 已采集 `guessed`（蒙对标记）、`responseMs`（作答耗时）、`retrievalStrength`（检索强度信号）并传入 `reviewWord(opts)`；`word-repo.js:reviewWord` 的**普通复习分支**调用 `scheduleReview` 时**未透传这三个信号**——只有"取消熟词"分支用到 `guessed`（走 P2-1 的 FSRS guessed 分支）。
- 对照卡片侧 `repo.js:review()`：同样调用 `scheduleReview`，**同样未透传 `retrievalStrength`**（`guessed`/`responseMs` 在卡片侧由 `scheduleReview` 内部按 rating 推断，不依赖调用方传入）。
- **后果**：FSRS 的 `retrievalStrength`（检索强度，影响间隔的置信度修正）在**全库无任何消费点**——采集、落库（`wordReviews.retrievalStrength` 字段存在）、同步（manifest 含该字段）三段都通，唯独调度端不读。信号链"采集→落库→调度"断在最后一段，属于**花了三段成本、收益为零**的半实现。
- **修复**：`word-repo.js:reviewWord` 与 `repo.js:review` 的 `scheduleReview` 调用补传 `retrievalStrength: opts.retrievalStrength`；`srs.js:scheduleReview` 的 FSRS 分支消费该值（已有参数位，确认 `fsrsSchedule` 是否接收并参与计算）。补 1 条回归：带 retrievalStrength 的复习间隔与不带时不同。
- **定级 P2 理由**：算法层信号断链，影响 FSRS 调度精度但非崩溃，且涉及两侧（卡片+单词）统一改动。

**R16-4 `search-service` 截窗的"数组对象先全量 stringify"次级成本 + 动态 key 家族无完整性单测**
- `rowMatches` 对 `meta`（对象）/`tags`（数组）等结构化字段先 `JSON.stringify` 全文再截窗——大 `meta`（如 AI 分析结果含 resultData）stringify 后可能远超 500 字符，**截窗只省了匹配成本、没省序列化成本**，首屏搜索大文档时 stringify 仍是 O(全量)。
- 与 round14 P3-4 同源：动态拼接 key（`t('views.x.' + key)` 15 处）的字典完整性无单测保障，新增动态键家族漏配时正向闸不报、运行时回退 key 原文。
- **修复**：`rowMatches` 对对象字段改为"按已知子键逐值匹配"（复用 `fields` 配置里的字段路径），避免全量 stringify；补 1 条"动态键家族完整性"单测（遍历字典所有以 `.` 结尾的键，断言其子键集合在 zh/en 一致且非空）。

## 3. 交叉分析：可拓展 / 可优化 / 需修复

1. **R16-1**（P1）：`deleteCard` 补 review 墓碑 + `restoreFromTrash` 清墓碑——数据协同孤儿行，最优先；

### 可拓展
1. **思维导图节点交互**：R16-2 修好后，导图节点已持有稳定 cardId（P2-7 红利）——可顺势加"点击节点跳转卡片详情/高亮图谱对应节点"，目前节点只显示文本、无交互。cardId 键化是这次白捡的扩展基础。

2. **`rowMatches` 结构化字段按子键匹配**：见 R16-4，避免全量 stringify。

### 7.4 方法论备忘
