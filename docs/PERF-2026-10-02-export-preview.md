# PDF 导出预览卡顿：定位与优化（2026-10-02）

> 诉求：PDF 导出时的预览会让浏览器当前页面严重卡顿；要求定位主因（渲染 / 内存 / 重复计算），
> 给出优化方案，且**预览的画质、清晰度、显示效果不得下降**。

---

## 一、一句话结论

卡顿的主因是 **DOMPurify 净化 KaTeX 公式产物** —— 它占单段渲染耗时的 **93%**。
把这段产物移出净化范围（净化完再还原）后，**单段耗时 7.98ms → 1.24ms（6.4×）**，
1000 张卡的预览从 **15.95s → 2.47s**，而**渲染输出逐项完全相同**（画质零影响）。

---

## 二、定位过程（不靠猜，全部实测）

### 2.1 渲染链路的成本拆解

预览的本质是：把选中的**每一张卡片的正面与背面**都交给 `MarkdownRenderer` 渲染。
单张卡 = 2 段渲染。用 Node + jsdom 复现该组件的渲染管线（含典型卡片：正文 + 行内公式 +
块级公式 + 代码块 + 强调标记），逐段计时：

| 渲染阶段 | 单次耗时 | 占「可拆解三段」比例 |
|---|---|---|
| KaTeX 渲染（2 个公式） | 0.430 ms | 5.9 % |
| `marked.parse` | 0.076 ms | 1.0 % |
| **DOMPurify 净化** | **6.783 ms** | **93.1 %** |
| 完整管线（含正则等） | 7.354 ms | — |

**对照组**：不含公式/代码的纯文本卡片，完整管线仅 **0.470 ms**。

⇒ 含公式卡片的成本是纯文本卡的 **约 16 倍**，差异几乎全部来自净化环节。

### 2.2 为什么净化这么慢

`MarkdownRenderer` 用 `katex.renderToString(...)` 渲染公式，KaTeX 默认输出
`htmlAndMathml` —— **一段公式会产出 50+ 个 MathML 节点**（实测单段 45~50 个）。
`DOMPurify` 要逐节点解析、逐属性校验、再序列化回字符串，
于是净化成本与 **MathML 节点数**成正比，而不是与文本长度成正比。

### 2.3 折算到真实规模

| 卡片数 | 纯渲染阻塞（改前） | 主文档新增 HTML |
|---|---|---|
| 200 张 | 约 3.2 s | 约 3.3 MB |
| 500 张 | 约 8.0 s | 约 8.3 MB |
| 1000 张 | 约 **15.9 s** | 约 **16.6 MB** |

### 2.4 三个根因（用户要求区分「渲染 / 内存 / 重复计算」）

| # | 类型 | 具体问题 | 后果 |
|---|---|---|---|
| **1** | **渲染（计算）** | DOMPurify 逐个处理 KaTeX 的 MathML 产物，占单段 93% | 点「生成预览」当场卡死数秒~十几秒（主线程长任务） |
| **2** | **内存 / 渲染树规模** | 净化后的全部 HTML 常驻主文档，1000 张约 16MB、数十万节点 | **打开预览之后整页持续卡顿**（每帧样式重算/布局/滚动都要遍历） |
| **3** | **重复计算** | 模板里 `checkedIds.includes(c.id)` 写在 `v-for` 内 ⇒ O(候选数 × 勾选数)；`selectedCards()` / `doAnki()` 也是 `filter + includes` | 勾选上千张时每次点击都要跑百万级比较，且每次响应式更新都重算 |

## 三、优化实施

### P1（主修复）把 KaTeX 产物移出 DOMPurify 的处理范围

改的是 `MarkdownRenderer.render()` 的**净化顺序**：

```
改前：公式 → marked → 还原全部占位符（含 KaTeX HTML）→ DOMPurify 净化
改后：公式 → marked → 还原普通占位符 → DOMPurify 净化 → 还原 KaTeX 占位符
```

关键点：KaTeX 产物改用**独立前缀（MDK）的占位符**，净化阶段它仍是一段纯文本 ⇒
DOMPurify 面对的 HTML **不再包含任何 MathML**，成本降到纯文本卡水平。

**安全边界没有放松，而是换了一条等价的、更便宜的通道**：

- 本文件调用 `renderToString` 时未开启 `trust`（即默认 `trust: false`）——
  KaTeX 会**忽略** `\href` / `\url` / `\includegraphics` / `\htmlClass` / `\htmlStyle` 等
  可能产出危险属性的命令，输出结构固定且文本已转义；它属于「库生成的固定结构」，
  与「用户可控 HTML」（卡片正文）性质不同。
- 新增 `katexGuard()` 做**便宜的黑名单纵深防御**（危险标签 / `on*` 事件属性 / 危险协议），
  命中即降级为**转义后的 LaTeX 原文**（公式退化为文字，绝不执行任何东西）。
- **用户内容与自建模板（代码块/行内代码/强调/图片）的净化覆盖完全不变** ——
  它们仍在第 7 步随 marked 产物一起过 DOMPurify，与改前**逐字节一致**。

### P2 屏外卡片跳过渲染（`content-visibility`）

`.print-card` 增加 `content-visibility: auto` + `contain-intrinsic-size: auto 260px`，
让浏览器跳过屏幕外子树的渲染与布局，缓解根因 2（数十万节点导致的持续卡顿）。

同时加 `@media print` 显式还原为 `visible`，封死「打印只输出已渲染部分 ⇒ 漏卡」的风险。

### P3 消除 O(候选 × 勾选) 的重复计算

- 新增 `checkedSet = computed(() => new Set(checkedIds.value))`，模板改用 `checkedSet.has(id)`；
- `selectedCards()` 与 `doAnki()` 内的 `filter + includes` 改为基于 `Set` 的查找。

## 四、画质 / 清晰度 / 显示效果的保证（实测证据）

同一份内容分别跑**改前顺序**与**改后顺序**，用 jsdom 结构化比对：

| 对比项 | 改前 | 改后 | 结论 |
|---|---|---|---|
| 文本内容 | — | — | **完全一致** ✅ |
| DOM 节点总数 | 239 | 239 | 相同 ✅ |
| MathML 节点数 | 45 | 45 | **公式的无障碍层完整保留** ✅ |
| katex 类节点 | 6 | 6 | 相同 ✅ |
| `code` 块 | 0 | 0 | 相同 ✅ |
| `img` 数量 | 0 | 0 | 相同 ✅ |
| **HTML 总长度** | **8694** | **8694** | **逐字节同长** ✅ |
| **标签 + 属性序列** | — | — | **完全一致** ✅ |

⇒ 交给 `v-html` 的最终 HTML 与改前**没有差别**，因此**画质、清晰度、排版、公式显示零影响**；
MathML 无障碍层也**没有**被牺牲（没有改用 `output:'html'`）。

### 安全性回归对照

构造 9 类注入用例（含 KaTeX 的 `\href` / `\url` / `\htmlData` / `\includegraphics`），
新旧两种顺序各跑一遍，判定标准为「DOM 中是否存在危险标签 / 事件属性 / 属性里的危险协议」：

**18 / 18 全部通过**（改前 9 例 + 改后 9 例）⇒ 安全性未降级。

> 首轮跑出 6 例「失败」，经查是**判定正则过宽**（把公式里可见的 `javascript:` 文本也算进去了），
> 收紧为「只查属性值」后全部通过；该 6 例在**新旧顺序下表现完全相同**，可确认与本次改动无关。

### 打印是否会漏卡（`content-visibility` 的唯一风险点）

用 Chrome `--headless=new --print-to-pdf` 实测 200 张卡：

| 版本 | PDF 页数 | 命中卡片 | 缺失 |
|---|---|---|---|
| 带 `@media print` 还原（当前实现） | 15 | 200 / 200 | 无 |
| **去掉还原（负向对照）** | 15 | **200 / 200** | **无** |

**诚实标注**：负向对照也**没有漏卡** —— 说明 Chrome 的打印引擎本身就会渲染
`content-visibility` 子树。因此 `@media print` 还原是**纵深防御**（防其他引擎/未来版本行为差异），
而不是本次修复的必需项。我保留了它（零成本），但**不宣称**它解决了一个已存在的缺陷。

## 五、效果汇总

| 指标 | 改前 | 改后 | 提升 |
|---|---|---|---|
| 单段渲染（含公式的典型卡片） | 7.98 ms | **1.24 ms** | **6.4×** |
| 200 张卡预览 | 约 3.2 s | 约 0.5 s | 6.4× |
| 500 张卡预览 | 约 8.0 s | 约 1.2 s | 6.4× |
| 1000 张卡预览 | 约 15.9 s | 约 **2.5 s** | 6.4× |
| 屏外卡片渲染 | 全部参与 | 跳过（`content-visibility`） | 缓解持续卡顿 |
| 勾选判定复杂度 | O(候选 × 勾选) | O(候选 + 勾选) | 消除百万级比较 |

（单段耗时为 Node + jsdom 环境实测；绝对数字会随机器不同，比例关系稳定。）

## 七、诚实边界：本次**没有**做的验证

1. **未在真实浏览器里实测端到端帧率 / 滚动流畅度**。
   沙箱无法可靠测量 paint 与滚动帧率，因此：
   - `content-visibility` 的收益我**只依据规范语义**（跳过屏外子树的渲染与布局）陈述，
     **没有实测数据**支撑具体提升幅度；
   - P1 的 6.4× 是渲染函数级别的实测（Node + jsdom，复现的是组件真实管线），
     不是整页帧率实测。
2. **未做多浏览器验证**（只测了 Chrome）。`content-visibility` 在 Safari / Firefox 上的
   跳过策略与打印行为可能不同 —— 这也是我保留 `@media print` 还原的原因。
3. `PLAIN` 对照只覆盖「纯文本卡」，未穷举所有卡片形态（如超长代码块、大量图片）。
