## 一、修复清单（每条都做了负向对照）

### D — 删卡级联删批注时补写墓碑（`sync.js`）

设备 A 删卡时走「先写墓碑 → 再物理删」；但设备 B **收到** A 的删卡指令后级联清理批注时**只删行、不写墓碑**。

后果：若这条批注在**第三台设备**上也存在（那台还没收到卡片墓碑），B 删掉后没有墓碑传出去，
下轮三方同步时对方会按「新行」把它灌回来（`cardAnnots` 是 `updatedAt` 整行 LWW、不参与 idOnly 幂等）
⇒ 删除失效，整条收敛链只能指望末尾的 `sweepOrphanRows` 兜底（且它是 fire-and-forget、失败仅 warn）。

改为：`toArray()` 收 id → `tombstones.bulkPut(kind:'cardAnnot')` → `bulkDelete`，与 `repo.deleteCard:655` 完全同口径。

**负向对照**：去掉墓碑写入后，新增断言使 `sync-audit.test.mjs` 的 v35 用例变红（`not ok 7`）；恢复后全绿。

## 二、审计发现的系统性问题：删同步表图片普遍漏写墓碑

### 怎么发现的

做完 D 之后，我怀疑「漏写墓碑」不是孤例，于是写了一个扫描脚本：
把 `sync-manifest.js` 里的同步表清单提出来，再扫全仓所有物理删除点，检查每处**前后 25 行内是否有墓碑写入**
（排除 `sync.js` —— 它删的是「已被对端墓碑判死」的从属行，语义不同）。

结果：**68 处同步表物理删除，63 处附近有墓碑，5 处没有**。

### 逐个核对后的结论

| 位置 | 表 | 判定 |
|---|---|---|
| `repo.js` `cleanupOrphanImages` | images | ❌ **真缺口**（见下） |
| `views/Cards.vue:558/568` | images | ❌ **真缺口**（本轮已修） |
| `views/Health.vue:98/121` | images | ❌ **真缺口**（本轮已修） |
| `graphAuto.js:256` | graphEdges | ✅ 不是问题：删的是 `kind==='auto'` 的派生边，**auto 边不进同步**（有注释说明），写墓碑只会让墓碑表无意义膨胀 |
| `services/word-meaning.js:149` | syllabusMeanings | ⚠️ 不是活跃问题：该分支由 `opts.prune` 控制，而**全仓无任何调用方传 `prune: true`** ⇒ 死路径 |

### 三个真缺口的共同后果

`images` 是同步表且按 `idOnly` 幂等 ⇒ **本机删掉的图会在下一次同步被对端/hub 原样灌回来**。
用户点「清理孤儿图片」后，换设备或下次同步图又出现 —— 清理**静默失效**。

而项目标准口径是明确的（`repo.js:698` 注释写着「round26 D3：**先写墓碑、后物理删**」）：

```js
await db.tombstones.bulkPut(orphanImages.map(id => ({ id, kind: 'image', deletedAt: now() })));
await db.images.bulkDelete(orphanImages);
```

`Cards.vue` 与 `Health.vue` 是视图层直接 `db.images.delete(id)`，**绕过了这个口径**。

### 修法（沿用 round122 的「收口」思路，而不是逐处打补丁）

1. `repo.js` 新增 **`deleteOrphanImages(ids)`**：单事务内「写 `kind:'image'` 墓碑 → 物理删」，返回删除数量。
2. `Cards.vue`（孤儿图面板，2 处入口）与 `Health.vue`（「清理孤儿图片」+「一键修复」，2 处入口）
   全部改为调用它；两个 .vue 不再直接碰 `db.images`。
3. `cleanupOrphanImages`（一个**没有任何调用方的死导出**，契约却要求「调用方先写墓碑」——极易踩坑）
   改为**自包含**墓碑，将来谁调用都不会漏。

**负向对照**：去掉 `deleteOrphanImages` 里的墓碑写入后，3 个行为断言变红（`not ok 1/2/3`）；恢复后 6/6 全绿。

## 三、自我纠正：F 这一条我上一轮判断错了

上一轮我说 `annot.level` 是「全仓无读取方的死字段」，准备删掉它。动手改完后我去查测试，
发现 **`tests/card-annot.test.mjs` 有 3 处断言把它钉成了契约**：

- `assert.equal(row.level, 4)` —— 快照必须记录写批注时的等级
- `assert.equal(orphan.level, null)` —— 取不到时必须是 null（不是 0、不是 undefined）
- `assert.match(src, /db\.cards\.get\(/, '允许读卡片取 level 快照')` —— 源码里必须保留这次查询

也就是说：它**不是遗漏，是有意保留的设计**（只是当前 UI 没展示）。

**收益 vs 成本重新算**：删除能省的只是一次主键查询（微秒级）；成本是改 3 处断言 + 推翻一个已固化的设计意图。
**结论：不修，已回滚**。我保留了一个注释，写明「下一轮不要再把它当死字段重复开单」并附上理由
（项目里已有同类做法，如 `round80-algo-guards.test.mjs:198`）。

> 这条纠正本身也是本轮的价值：**「看起来没人用」不等于「没人依赖」**——`grep` 生产代码查不到读取方，
> 但测试同样是消费者。判断死代码时必须连测试一起查。

## 五、为什么 G（墓碑表主键）**不建议**修

`db.js:28`：`tombstones: 'id, deletedAt'` —— 主键是单列 `id`，却靠 `kind` 区分语义；
`db.tombstones.put({id, kind})` 是整行覆盖，`restoreFromTrash` 里 `bulkDelete(annots.map(a => a.id))` 也不按 kind 过滤。

- **收益**：避免两个不同 `kind`、相同 `id` 的墓碑互相覆盖/误删。而 id 是 `uid()`（随机 UUID），
  碰撞概率约 2⁻¹²² —— 现实中不会发生。
- **代价**：改复合主键 `[kind+id]` 是 **schema 版本升级（v36）+ 全量数据迁移 + 所有墓碑读写点改造**
  （`applyTombstones` / `mergeTombstones` / `pruneTombstones` / `deleteCard` / `deleteAnnot` / `sweepOrphanRows` …）。
  一旦迁移出错，影响的正是「删除同步」这条最难排查的链路。

**收益极小、代价与风险极大 ⇒ 保持现状**。（若将来真的换了 id 生成策略、不再是随机 UUID，再重新评估。）
