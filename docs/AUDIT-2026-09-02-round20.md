## 2. 新发现

### CI-1（P1）：CI 门禁仍处于诊断模式——测试失败不阻断部署

- **位置**：`.github/workflows/deploy.yml`（HEAD `7e55bb1`）
  - `:49-62` `set +e` + `npm test` 结果写入 `npm-test.log`，exit code 被吞
- **根因**：`6e7b5f6`（ci(final), 21:10）声称「恢复 npm test 阻塞门禁」并删除 `_ci_case_check.mjs`；但随后 `e5b1df4`（ci(diag): Run #72, 21:56）和 `7e55bb1`（ci(diag): Run #73, 22:32）又重新引入 `set +e` 诊断模式——**ci(final) 的阻塞门禁在两轮诊断提交后被覆盖**。
- **影响**：当前 CI 对任何测试回归（包括 i18n 闸门、业务逻辑回归）**完全静默**——失败的 npm test 不阻断 build，不阻断 Pages 部署。下一次代码引入回归时，CI 不会拦截，用户无感知。
- **验证**：当前 deploy.yml 的 `Run tests` 步骤无 `if: success()` 或 `set -e`，且注释明确写「diagnostic, never fail the job」。
- **修复**：17c64af 的 i18n 路径归一已到位（本轮复核确认），诊断目的已达成。应恢复 `set -e`（或删掉 `set +e`），让 npm test 失败时阻断后续 build/deploy。

### CI-2（P2）：CI 诊断日志公开部署到 GitHub Pages

- **位置**：`.github/workflows/deploy.yml:67-70`
  - `mkdir -p dist/_ci && cp -v npm-test.log dist/_ci/` → 随 Pages 部署到公网
- **根因**：诊断阶段为方便拉取 npm test 输出（Run #70-#72 排查 1 秒崩），将日志复制到 dist。诊断目的已达成，但日志收集步骤未撤除。
- **影响**：`npm-test.log` 包含：Node 版本、OS 信息（`uname -a`）、完整测试输出（777 条测试名 + 耗时）、文件路径。虽无 secret，但暴露内部测试拓扑和路径，且随每次 push 自动更新。
- **修复**：恢复阻塞门禁后，删除「Publish CI diagnostic logs to dist/_ci」步骤。

### CI-3（P3）：CI i18n 路径归一修复质量确认

- **位置**：`scripts/check-view-i18n.mjs:20` `const rel = (abs) => relative(root, abs).replace(/\\/g, '/');`
- **核验**：修复前 Windows baseline 存的是绝对盘符路径（`E:\\...\\src\\repo.js`），Linux CI 生成的是相对路径 → key 永远对不上。修复后用 `path.relative(root, abs)` + `.replace(/\\/g, '/')` 统一为 POSIX 相对路径。
- **结论**：✅ 修复正确，Windows/Linux 下 rel 结果一致。本轮本地 npm test 777 全绿确认无回归。
