# 局域网同步失败根因分析与方案对比（2026-09-10）

> 场景：手机 / 平板 / 电脑同处一个局域网；三端访问 **GitHub Pages（HTTPS）** 上的页面；
> 点同步 → 三端都提示「同步失败」。页面的同步中枢地址填的是 `http://<电脑IP>:18080`。

---

## 一、结论速览

**不是"必须 HTTP"的问题，而是"页面是 HTTPS 时，接口也必须是 HTTPS"。**
HTTPS 公网页面请求 `http://<私网IP>:18080` 需要同时跨过三道浏览器门槛，目前**三道全都没过**：

| 层 | 门槛 | 现状（GitHub HTTPS 页面 → http://私网IP） | 是否可修 |
|---|---|---|---|
| L1 | **混合内容（Mixed Content）** | Chrome 142+ 对「私网 **IP 字面量**」目标**已豁免**硬阻止（改由 LNA 权限门控）；**Safari/iOS 无此豁免 → 仍然硬阻止** | iOS 上无法绕过（除非接口改 HTTPS） |
| L2 | **本地网络访问权限（LNA / 原 PNA）** | Chrome/Edge **142 起默认启用**：公网页面 → 本地/回环地址需**用户授权**（弹窗或站点设置里允许）；未授权 → 拒绝 | 可修（用户授权），但**仅 Chrome/Edge**；iOS Safari 没有这个机制 |
| L3 | **CORS** | hub 默认只放行「同源 / localhost / 私网 IP 的 Origin」，**不放行 `hui-shang-qing.github.io`** → 预检即拒 | **必须改（配置即可）** |

> 关键：**L3 是确定性的、我们自己的问题**——即使 L1/L2 都过了，CORS 也会把请求拒掉。
> 而 L1 在 iOS 上无解，所以**"保留 GitHub HTTPS 页面 + 用 HTTP 接口"这条路在 iPhone/iPad 上走不通**。

---

## 二、本机实证（可直接复现）

用无头 Chrome + CDP 做了三组对照实验（2026-09-10，Windows/Chrome）：

**实验 1：HTTPS 公网页面发起请求**（页面取 `https://example.com`，等价于 GitHub Pages 场景）

| 目标 | 结果 | 浏览器日志原文 |
|---|---|---|
| `http://192.168.x.x:18099/health`（私网 IP） | ❌ Failed to fetch | `Mixed Content: ... requested an insecure resource 'http://192.168.x.x:18099/...'` + `Access to fetch ... has been blocked by CORS policy: Permission was denied for this request to access the 'local' address space.` |
| `http://127.0.0.1:18099/health` | ❌ Failed to fetch | `Permission was denied for this request to access the 'loopback' address space.` |
| `http://localhost:18099/health` | ❌ Failed to fetch | 同上（loopback） |

> 注意：**localhost 不再是"免检通道"**——公网 HTTPS 页面访问本机回环同样需要 LNA 授权。
> 且这次实验里服务器已返回了 `Access-Control-Allow-Private-Network: true`，仍被拒 → 说明新模型是「**权限**」而非「响应头」。

**实验 2：HTTP 页面发起请求（同源 / 跨到私网 IP）**

| 目标 | 结果 |
|---|---|
| HTTP 页面(`127.0.0.1`) → 同源 `/health` | ✅ 200 |
| HTTP 页面(`127.0.0.1`) → `http://192.168.x.x:18101/health` | ✅ 200 |

> **HTTP 页面（哪怕在回环上）请求私网 HTTP 完全畅通** —— 这正是"以前能用"的技术基础。

**实验 3：因果验证**（关闭 LNA 检查 / 尝试授予权限）

| 配置 | 结果 |
|---|---|
| 默认 | ❌（LNA 权限拒绝） |
| `--disable-features=LocalNetworkAccessChecks` | ❌ **退回纯混合内容阻止**（`This request has been blocked; the content must be served over HTTPS`）→ 说明"LNA 豁免"是混合内容的**唯一放行通道**，关掉它只会更严 |
| CDP 授予 `localNetworkAccess` 权限 | 接口返回 OK，但无头环境仍拒绝（无 UI、权限未真正生效） |

> 结论：**在真机（有界面）浏览器上，首次同步时会弹「允许访问本地网络设备？」提示**；
> 用户在提示里点允许（或站点设置里改 Allow）后，Chrome/Edge 才有机会连通 —— 但这**只解决桌面与 Android**。

## 三、为什么"很早以前的版本可以同步"

代码与文档都印证了：**早期的主用法是"手机浏览器直接打开中枢自带的页面"，而不是 GitHub 页面。**

证据 1 —— `src/views/Sync.vue:24-26`（设计意图写在代码里）：
```js
const isOnGhPages = /\.github\.io$|pages\.dev|vercel\.app|netlify\.app/.test(location.hostname);
const isHttps = location.protocol === 'https:';
const defaultHub = isOnGhPages ? '' : (isHttps ? '' : location.origin);   // HTTP 页面 → 默认同源
```
→ 页面是 HTTP 时，中枢地址**默认填当前源**（同源、零配置、必成功）；GitHub 页面时才留空让用户手填。

证据 2 —— `sync-hub/hub.js:6`：中枢**同时托管前端**（`dist/`），手机打开 `http://<电脑IP>:18080` 就是应用本身。

证据 3 —— `docs/使用文档.md:13/141`：推荐流程写的就是「手机浏览器打开 `http://电脑IP:18080`（直接打开中枢提供的应用）→ 进同步页填同一地址 → 保存」。

证据 4 —— 前端**早就内置了这个失败提示**（说明该限制此前已出现过）：
`src/i18n/views/sync.js:110`：*"当前部署在 GitHub Pages（HTTPS），浏览器会阻止 HTTPS 页面请求 HTTP 内网 Hub，表现为「Fail to fetch」。请用手机/平板浏览器直接打开电脑端 Hub 地址（http://<电脑IP>:18080）"*
`src/sync.js:610`：HTTPS 页面下 fetch 抛 TypeError 时，直接抛出"混合内容拦截"的针对性报错。

**所以"以前能成功"= 当时访问的是 hub 自托管页面（HTTP，同源）**，三层门槛全不触发；
后来改从 GitHub HTTPS 页面进同步 → 三层门槛同时生效（且 Chrome 142 起 LNA 默认开启，把"半可用"也堵死了）。

## 四、方案对比（前提：页面继续用 GitHub HTTPS）

| 方案 | 做法 | 前提条件 | 限制 | iOS | Android | 桌面 | 改动范围 |
|---|---|---|---|---|---|---|---|
| **1. 同源入口（推荐·零信任操作）** | 同步时用手机浏览器打开 `http://<电脑IP>:18080`（hub 自带页面），在其「同步」页操作；日常仍用 GitHub PWA | hub 在跑 + 防火墙放行 18080 + 同 WiFi | 需要多开一个入口；HTTP 页面无法安装 PWA（仅同步用，影响小） | ✅ | ✅ | ✅ | **零代码**；可选小改动：GitHub 页面加「打开中枢」按钮/二维码 |
| **2. hub 升级 HTTPS（自签证书）** | hub 用 `node:https` + 自签 CA（**SAN 含 IP**）；页面仍 GitHub | 每台设备安装并信任该 CA | iOS 需两步（装描述文件 + 证书信任设置里"完全信任"）；Android 装用户证书；桌面导入信任库；**换 IP/换网要重签**；iOS 限制证书有效期（>825 天不被信任） | ⚠️ 可行但繁琐 | ⚠️ 可行但繁琐 | ⚠️ | 中等：hub 加 https 启动 + 证书生成脚本 + 前端允许 https 地址 |
| **3. Tailscale（推荐·多端最省心）** | `tailscale serve --bg 18080` → 得到 `https://<机器>.<tailnet>.ts.net`，**自动合法证书** | 各设备装 Tailscale 并登录同账号（个人免费） | 不算"纯局域网"（走 tailnet，点对点加密）；需联网 | ✅ | ✅ | ✅ | **零代码**（仅部署）；建议配 `HUB_ALLOW_ORIGIN` |
| **4. Cloudflare Tunnel** | `cloudflared tunnel --url http://localhost:18080` → 临时 `https://xxx.trycloudflare.com` | 电脑联网 | 免费隧道 URL 每次会变、速度受中转影响、可能有限流；隐私上数据经第三方边缘（虽有 TLS） | ✅ | ✅ | ✅ | 零代码；要固定域名需自有域名 + 命名隧道 |
| **5. 仅浏览器放行（桌面/Android）** | hub 放行 Origin + 用户在浏览器里把「本地网络访问」设为允许（首次会弹窗） | Chrome/Edge 142+ | **iOS Safari 无 LNA → 不可用**；用户可能误点拒绝且难发现；换浏览器/清数据后需重授权 | ❌ | ⚠️ 取决于版本/提示 | ⚠️ 可用 | 配置 + 前端提示；不可作为唯一方案 |
| **6. 手动导出/导入 JSON（兜底）** | 用现有「手动备份 / 导入」+ 文件分享（AirDrop/微信/文件 App） | 无 | 非一键；需人工搬运 | ✅ | ✅ | ✅ | 零代码 |

## 五、推荐路线

**首选：方案 1（同源入口）** —— 立即可用、零信任操作、三端一致。日常用 GitHub PWA 学习，需要同步时切到中枢页面点一下（数据是同一份 IndexedDB 数据域，互不冲突）。

**追求"始终留在 GitHub 页面"：方案 3（Tailscale）** —— 唯一能让 iOS/Android/桌面**都免去证书操作**的路径，且拿到的是合法 HTTPS 域名，天然绕过 L1/L2。

**次选：方案 2（自签 HTTPS）** —— 不想引入第三方客户端时可用，但要接受"每台设备装证书 + 换 IP 重签"的维护成本。

**无论选哪个，都建议先做这两件配置/改动（都是必要项，成本极低）：**
1. 启动 hub 时设置 `HUB_ALLOW_ORIGIN=https://hui-shang-qing.github.io`（**当前默认不放行该 Origin，是确定性失败原因**）；
2. 前端同步页在「HTTPS 页面 + HTTP 中枢地址」组合下，把引导做得更直接：一键跳中枢页面 / 显示二维码 / 复制地址（现有代码只有一段静态提示）。

## 六、排查验证方法（按顺序，5 分钟定位）

1. **先排除网络与中枢本身**
   - 电脑上：`node sync-hub/hub-smoke.mjs http://<电脑IP>:18080 <密码>`（项目自带一键冒烟：预检/401/静态/PUT/GET）
   - 手机浏览器直接打开 `http://<电脑IP>:18080` → 能出应用页面 = 中枢与局域网 OK
   - 命令行：`curl -sv http://<电脑IP>:18080/health`
   - 防火墙（Windows，管理员）：`netsh advfirewall firewall add rule name="SxyBrick Hub 18080" dir=in action=allow protocol=TCP localport=18080`
2. **再看浏览器报错（最关键）** —— 桌面 Chrome 打开 GitHub 页面 → F12 Console → 点同步，对号入座：
   - `Mixed Content ... requested an insecure resource 'http://192.168.x.x:18080/...'` → L1
   - `blocked by CORS policy: Permission was denied for this request to access the 'local' address space` → L2（未授权）
   - `Access-Control-Allow-Origin ...` / 无 CORS 头相关报错 → L3（hub 未放行 Origin）
   - 前端只会统一显示「同步失败」，**必须看 Console 才能区分**（移动端可临时用 `eruda` 之类注入 Console）
3. **确认 L2 的授权状态**：地址栏锁图标 → 站点设置 → 找 **「本地网络访问」/「Local network access」**（Chrome 142+）是否被拒；改 Allow 后刷新重试
4. **确认"限制只针对 HTTPS 入口"**：在电脑浏览器打开 `http://<电脑IP>:18080`，用该页面的「同步」页点同步 → **若成功，即证明第 1、2、3 层限制全部由"HTTPS 页面"这个入口引发**
5. **查浏览器版本**：地址栏 `chrome://version`（≥142 才有 LNA 默认限制）

## 七、一句话总结

- 同步接口**不必是 HTTP**；但**页面是 HTTPS 时，接口也必须 HTTPS 且证书受信任**，否则 iOS 无解。
- 三端同时失败是因为：**改用 GitHub HTTPS 页面后，混合内容 + 本地网络访问权限 + CORS 三层同时生效**；其中 CORS 一层是我们自己的配置问题（未放行 GitHub Pages 域），必须修。
- 旧版本能成功，是因为当时**跟着文档走的是"打开中枢自带页面"（HTTP、同源）** —— 这条路径今天依然可用，是本轮最省事的推荐方案。
