## 3. P1（数据错误 / 可重复计入，1 项）

### R19-1 Pomodoro 同源双标签页：同一轮专注被 `addPomoSession` 双写，番茄数/成就/长休判定各 +2
- **位置**：`src/views/Pomodoro.vue`
  - `:40` `let lastPeerFinish = 0;`（**模块作用域，每个标签页各持一份独立副本**）
  - `:92-99` `start()` → `timer = setInterval(tick, 1000)`
  - `:171-186` `restore()`：读 localStorage `sxy_pomo_state`，`if (s.running && s.endTs)` 且 `remain > 0` → `running.value = false; start()`
  - `:128-150` `finish()`：去重仅 `if (Date.now() - lastPeerFinish < 5000)`（:136），否则 `addPomoSession`（:143）
  - `:214-222` `bc = new BroadcastChannel('sxy_pomo')`；`onmessage` 收到 `pomo-finish` → `lastPeerFinish = Date.now()`（:219）
- **根因**：两个同源标签页打开时**各自** `restore()`，都读到共享的 `sxy_pomo_state`（running=true）→ 都调 `start()` 起独立 `setInterval`。`finish()` 的去重**只**依赖 `lastPeerFinish` 5 秒墙钟窗口，而它是每标签页独立变量、仅在收到 bc 消息时更新。文件自身注释（:3、:18）已承认「后台标签页/锁屏时浏览器会节流 setInterval」——节流使两标签页的 `finish()` 实际触发时刻相差 **>5s** 时，后到者 `Date.now() - lastPeerFinish >= 5000` → 不去重 → `addPomoSession` 再写一次。全程**无「本轮已结算」的持久化幂等令牌**（roundId+settled）。
- **影响**：同一轮专注被写两次 → 今日番茄数 +2、成就 `pomo_1`/`pomo_50` 触发两次、同步包多一行 `pomoSession`、`countPomoToday % 4` 长休判定（:159）连带错乱。与 R18-6「专注数据可刷」同源——R18-6 修了单标签页「到点即满记」，**多标签页双写是它的漏网**。
- **修复**：`STATE_KEY` 加 `ownerTabId`（sessionStorage，每标签页唯一）——`restore` 见他人持有且 running 则只刷新 UI 不 `start()`；或 `finish` 入库前写 `settled: roundId` 幂等令牌（`addPomoSession` 对同 roundId 幂等去重）。

## 4. P2（逻辑缺陷 / 口径不一致，2 项）

### R19-2 WeeklyReport 番茄计数把 partial 计入，与其余三端口径直接矛盾
- **位置**：`src/views/WeeklyReport.vue:56,64`
  - `:56` `const pomosWeek = pomos.filter(p => p.startedAt >= from && p.startedAt < to);`（**无 `!partial`**）
  - `:64` `pomo: pomosWeek.length`
- **对照**：`repo.countPomoToday`（repo.js:1092）`rows.filter((s) => !s.partial).length`；`achievements.js`、`agent/analytics.js` 同为 `!s.partial`。
- **根因**：R18-6 引入 `partial` 标记「不足 FULL_FOCUS_MIN 不算番茄」后，countPomoToday / achievements / analytics 三端都加了 `!partial` 过滤，**WeeklyReport 的周聚合漏了这一端**——partial 会话（如专注 12 分钟的 partial 行）被计入「番茄 N 个」。
- **影响**：同一用户，日视图（番茄 3）/成就/分析 与 周视图（番茄 5）对不上；`pomoMinutes`（:65）把 partial 的分钟照计是对的，但「番茄个数」虚高。
- **修复**：`:64` 改 `pomo: pomosWeek.filter(p => !p.partial).length`，与其余三端统一。

### R19-3 rebuildIndex 清空后 docFiles（资料库）向量永不重建 → 资料库问答静默失效
- **位置**：`src/agent/retrieval.js`
  - `:168-170` `rebuildIndex()`：`await db.embeddings.clear(); return ensureIndex(9999, 999);`
  - `:120-129` `getStaleDocs()`：`const docs = await db.docs.limit(limit * 2).toArray();`——**只扫 `db.docs`，从不扫 `db.docFiles`**
- **对照**：`docs-lib.js:148` `indexDoc({ id: docId, text, subject: row.name })`——资料库文件导入时**确实建了向量**（docFiles 有 embeddings 行）。
- **根因**：增量重索引（`getStaleDocs`）与全量重建（`rebuildIndex` → `ensureIndex` → `getStaleDocs`）都只覆盖 `db.docs`（AI 对话文档），不覆盖 `db.docFiles`（资料库文件）。模型变更或手动「重建索引」后，`embeddings.clear()` 把 docFiles 的向量**一并清空**，但 `getStaleDocs` 扫不到 docFiles → **永不重建**。
- **影响**：`docs-qa`（docs-qa.js）对资料库文件的 RAG 检索静默返回空（向量没了），资料库问答在任意一次重建/换模型后**悄悄失效**；且 `getIndexStatus` 的 `docCoverage`（:279 `db.docs.count()`）只统计 db.docs，掩盖了这一失真。
- **修复**：`getStaleDocs` 增扫 `db.docFiles`（join docTexts 取 text）；或 `rebuildIndex` 后按 docFiles 列表逐个 `indexDoc`。

## 5. P3（健壮性 / 边界 / 算法有效性，2 项）

### R19-4 indexDoc `subject` 字段形状不匹配 → 资料库文件 subject 恒空
- **位置**：`src/agent/retrieval.js:95` `subject: doc.title || ''` vs `src/docs-lib.js:148` `indexDoc({ id: docId, text, subject: row.name })`
- **根因**：`indexDoc` 读 `doc.title`，但资料库调用方传的是 `doc.subject`（无 title 字段）→ `doc.title` 恒 undefined → subject 落 `''`。
- **影响**：所有资料库文件的 embedding `subject=''`，带 subject 的检索（`tools/index.js:723,756`）命中不到，`retrieveContext` 也显示不出标题（与 R19-3 叠加：资料库文件在 RAG 里基本不可用）。
- **修复**：`indexDoc` 改 `subject: doc.subject || doc.title || ''`，对齐两种调用形状（db.docs 传 title、docFiles 传 subject）。

### R19-5 FSRS 训练循环 first-non-improvement 即 break，从不缩小 lr → 个性化权重型 DEFAULT_WEIGHTS
- **位置**：`src/fsrs.js:283-290`
  - `if (cand.loss != null && (best.loss == null || cand.loss < best.loss)) { weights = next; best = cand; } else { break; }`
- **根因**：注释（:288）写「不再下降：缩小学习率继续尝试一轮，或提前结束」，但 else 分支直接 `break`，**从不缩小 lr**（注释承诺的「缩小 lr 继续」没实现）。lr=0.01 归一化梯度下，首个非严格下降步即终止，名义 30 轮实际只走极少量步。
- **影响**：训练出的个性化权重 ≈ `DEFAULT_WEIGHTS`，`App.vue:265`「已应用新权重 / 个性化记忆曲线」**名不副实**（用户花算力训练，得到的还是默认曲线）。
- **修复**：去掉 first-non-improvement 即 break，改为 lr 衰减（如连续 N 轮无改善才停），让 30 轮真正走完。

## 6. 交叉分析

### 6.1 根因模式（延续前轮，本轮新增一条强主线）
**本轮强主线：「单一事实源缺失」第三次复发。**
- round17 R17-32（clearTestData 手写 35 表清单漏 word 8 表）→ round18 R18-7（sync-status 手写两份清单漏 word 7 表）→ **round19 R19-2（`partial` 字段引入后，手写过滤三端、漏 WeeklyReport 第四端）**——同一根因三连：每加一个新字段/新表/新规则，所有「遍历/过滤/建索引」逻辑都要**手动同步每个消费端**，无统一事实源兜底。
- 本轮 R19-3/4 是它的 RAG 变体：`getStaleDocs`/`rebuildIndex` 的**索引来源硬编码成 `db.docs` 单表**，但数据实际有两源（`db.docs` + `db.docFiles`）；`indexDoc` 的 `subject` 字段形状按单一调用方写死。**索引来源 = 另一份硬编码清单。**
- **根治方向（跨三项一次性）**：① pomo 口径统一为单一谓词 `isPomoCountable(s)`，所有消费端（countPomoToday/achievements/analytics/WeeklyReport）调用它 + 一条「四端口径一致」回归断言；② RAG 来源表改为注册表驱动（`RAG_SOURCES = [db.docs, db.docFiles]`），`getStaleDocs`/`getIndexStatus` 遍历注册表；③ `indexDoc` 字段读取对齐多种调用形状。

### 6.2 幂等语义缺失（R19-1 与 round18 R18-10/14 同根因）
- round18 R18-10/14（导入循环无整体回滚、meta 读-改-写无事务）→ **round19 R19-1（Pomodoro `finish()` 无持久化幂等令牌，多标签页双写）**——同一「中断/并发不幂等」根因在状态机结算处再现。R18-6 修了单标签页结算，**多标签页是它的漏网**。
- 根治：结算动作统一带「幂等令牌」（roundId+settled），入库对同令牌幂等去重。

### 6.3 可拓展功能方向（非缺陷）
1. **`HEARTBEAT_CAP_MS` 产品边界确认**（R19-1 修复时顺带）：90s 心跳上限会把「标签页合法后台整跑 25 分钟」因节流空档记成偏短 partial——反作弊与真实专注的取舍，建议出「后台长专注」单独标记而非一刀切 partial（需产品拍板）。
2. **资料库 RAG 修复后（R19-3/4）做「索引覆盖率」可见化**：`getIndexStatus` 的 `docCoverage` 纳入 docFiles 后，UI 可显示「资料库 N 份文件已索引 / M 份待索引」，重建按钮旁给进度。
3. **FSRS 训练修复后（R19-5）出「训练收敛曲线」**：lr 衰减修好后，把每轮 loss 存下来，UI 画收敛曲线让用户看到「训练真的在收敛」——目前「已应用新权重」是个黑盒承诺。

### 6.4 可优化点（非 bug）
- `restore()` 对 running 状态「先 `running=false` 再 `start()`」（:180-186）：注释说「交给 start() 统一建计时器」，但 start() 内部又会 set `running=true` + 重置心跳锚点——多标签页场景下这个「假关再开」会重置 `lastSeen`（关页空档不计专注的正确行为），单标签页无碍，但语义绕，R19-1 加 ownerTabId 时一并理清。
- `getIndexStatus`（retrieval.js:285）`docCoverage` 只算 db.docs，R19-3 修复时应同步纳入 docFiles，避免「覆盖率数字」继续失真。
