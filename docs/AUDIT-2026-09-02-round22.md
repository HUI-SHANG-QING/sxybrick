## 1. 新增发现（与 round21 不重叠）

### P1 性能 · analytics.js 大表全量 toArray() → 内存峰值与 GC 压力

- **位置**：`src/agent/analytics.js:107,136-137,175,267,316,358,433,670,718`
- **成因**：`_getCrossModuleInsight` 在单次调用中并行执行 `db.reviews.toArray()` + `db.cards.toArray()` + `db.graphEdges.toArray()` + `db.plans.toArray()` + `db.docs.toArray()` + `db.memos.toArray()` + `db.aiChats.toArray()` + `db.pomoSessions.toArray()` —— 8 张表全量读入内存。对长期用户（reviews >10K 行、cards >2K 行），单次调用可分配 >50MB 临时对象。
- **影响范围**：每次打开分析面板 / 触发 AI 洞察 / 查看统计时执行。移动端低内存设备可能触发 GC 抖动甚至 OOM。
- **触发条件**：reviews >5K 且 cards >1K。
- **修改方向**：① 改用 `where().above()` 按时间窗口裁剪（如只取近 90 天 review）；② 用 `count()` + `limit(N)` 替代全量读取（统计场景不需要全部行）；③ 对 `toArray()` 结果加 LRU 缓存（同一会话内分析面板多次打开不重复查）。

### P2 性能 · importBackup JSON.stringify 逐卡比对 → O(n²) 序列化

- **位置**：`src/sync.js:621` `if (JSON.stringify(old) !== JSON.stringify(row)) { updated++; toWrite.push(row); }`
- **成因**：对每张合并后的卡片执行 `JSON.stringify(old)` + `JSON.stringify(row)` 做浅比较。每张卡片 ~20 个字段，JSON.stringify 涉及字符串分配 + 转义。千卡级导入（1000 卡）= 2000 次 JSON.stringify + 1000 次字符串比较。
- **影响范围**：Gist 备份恢复、Hub 同步拉取、手动导入备份。小数据量无感知，>500 卡时可感知延迟。
- **触发条件**：导入 >500 张卡片。
- **修改方向**：改用逐字段 `===` 比较（卡片字段都是原始类型或小数组），或比较 `updatedAt` 时间戳（只在 incomingupdatedAt > local updatedAt 时才写入，跳过无变化行）。

### P3 数据层 · snapshot 表 `rows` 字段内存占用无上限

- **位置**：`src/db.js:128` `snapshots: 'id, createdAt, kind'`，`src/repo.js` `saveSnapshot` 将全表数据 JSON 序列化存入 `rows` 字段
- **成因**：每次 `importBackup` 前自动快照（`opts.skipSnapshot=false` 时），将全部同步表的数据序列化为一个 JSON 对象存入 `snapshots.rows`。对 10K 卡 + 50K review 的用户，单个快照可达 10-30MB。30 天 TTL 内可累积 30+ 个快照 = 300-900MB IndexedDB 配额。
- **影响范围**：长期使用 + 频繁同步的用户。移动端存储配额紧张时可能导致 QuotaExceededError。
- **触发条件**：日均同步 >1 次，持续 30 天，数据量 >5K 卡。
- **修改方向**：① 快照改为增量（只存 diff 而非全量）；② 降低自动快照频率（如只在手动导入时快照，同步拉取不快照）；③ 压缩 `rows`（JSON gzip 或只存必要字段）。

### P4 业务层 · hub.js writeFileSync 阻塞事件循环

- **位置**：`sync-hub/hub.js:89-91` `writeFileSync(tmp, JSON.stringify(data)); renameSync(tmp, DATA_FILE);`
- **成因**：`saveData` 和 `saveScopedData` 使用同步文件写入。Hub 是单线程 Node HTTP 服务器，writeFileSync 会阻塞所有 pending 请求。对 >1MB 的 hub-data.json（10K 卡级别），写入耗时可达 10-50ms，期间其他设备的 PUT/GET 请求排队。
- **影响范围**：多设备同时同步时的延迟。单设备无感知。
- **触发条件**：hub-data.json >1MB + 多设备并发 PUT。
- **修改方向**：改为 `writeFile`（异步）+ `rename`（异步），或用 `fs.createWriteStream` 流式写入。需评估并发写入的原子性（rename 在 POSIX 上是原子的，Node 异步 rename 同理）。

### P5 业务层 · hub.js 200MB 请求体上限

- **位置**：`sync-hub/hub.js:213` `function readBody(req, limitBytes = 200 * 1024 * 1024)`
- **成因**：默认 200MB 请求体上限。恶意客户端可构造超大 PUT 请求消耗 Hub 内存（readBody 将全部 chunks 拼接为 Buffer → toString → JSON.parse）。Hub 运行在用户家庭电脑上，通常无防火墙保护。
- **影响范围**：Hub 进程内存。200MB JSON 解析后内存占用可达 400-600MB（V8 堆）。
- **触发条件**：恶意或配置错误的客户端发送超大请求。
- **修改方向**：降低上限至 50MB（实际数据包远小于此）；或改为流式 JSON 解析（避免全量加载到内存）。

### P6 性能 · graphAuto.js 重建时全量读取 graphEdges

- **位置**：`src/algorithms/graphAuto.js:244` `const existing = (await db.graphEdges.toArray()).filter(e => e.kind === 'auto');`
- **成因**：重建图谱时先读全表 graphEdges，再 filter 出 `kind === 'auto'` 的行做 bulkDelete。graphEdges 可能有数千条（含 AI 生成 + 智能推荐 + auto），全量读入内存再过滤浪费。
- **影响范围**：图谱重建操作（用户手动触发或自动触发）。
- **触发条件**：graphEdges >1000 条。
- **修改方向**：改为 `db.graphEdges.where('kind').equals('auto').toArray()` —— 但当前 schema 无 `kind` 索引。若加索引（schema v25），此查询可命中索引。临时方案：`db.graphEdges.filter(e => e.kind === 'auto').toArray()`（Dexie filter 虽是全表扫描但不创建中间数组）。
