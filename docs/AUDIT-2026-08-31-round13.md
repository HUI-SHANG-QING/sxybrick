## 1. 本轮新发现

### P1（3 项，均在单词模块）

**P1-A 回收站无法恢复 wordCard / wordGroup —— 30 天 TTL 后数据永久丢失**
`word-repo.js` 的删除流程正确写了 `trashItem(id, 'wordCard', {…})` 快照 + 墓碑，但 `repo.js:restoreFromTrash` 的 kind→table 映射只有 `card/memo/note/plan/doc/mindmap/docFile` 七种，**没有 `wordCard` / `wordGroup`**。后果链：
1. 用户误删单词卡 → 进回收站，页面 `kindLabel` 落回裸字符串 `wordCard`，`previewOf` 落回 `JSON.stringify` 原始 JSON；
2. 点「恢复」→ `restoreFromTrash` 返回 false → toast「不支持恢复」，**单词卡在回收站里永远无法恢复**；
3. 「恢复全部」批量路径（RecycleBin.vue:102）静默跳过（不计入 n，用户已确认「恢复 n 条」）；
4. 30 天后 `pruneTrash` 自动清快照 → **数据永久丢失，且无用户可感知的提醒**。

修复需同步处理两件事：映射补 `wordCard:'wordCards'` / `wordGroup:'wordGroups'`，且 `restoreFromTrash` 目前只还原 `db.reviews` / `db.cardGroupLinks` 两张附表——单词卡的 `_reviews` 要还原进 `db.wordReviews`、`_groupLinks` 要还原进 `db.wordGroupLinks` 并连带清 `wordGroupLink` 墓碑（否则恢复后下次同步被自己的墓碑再删一遍，与 cardGroupLinks 分支同型）。

**P1-B 取消熟词标记后，单词一年不进复习队列**
`word-repo.js:markFamiliar`：标记熟词时 `dueAt = now + 365 天`（设计如此，移出队列）；但**取消标记（value=0）时不还原 dueAt**。`WordBook.vue:116` 是 toggle（`markFamiliar(c.id, c.familiar ? 0 : 1)`），所以「取消熟词」后该词 `dueAt` 仍在未来约一年处，`dueWordCards`（`dueAt <= now` 过滤）永远不会把它排进队列——用户取消熟词后，这个词在单词本里「看得见、背不到」，最长失踪 365 天。
修复：取消时应把 `dueAt` 回写为 `now`（重新进入当日队列）或按原间隔重排；最小改动是 `if (v === 0) patch.dueAt = Math.min(cur.dueAt, now())`。

**P1-C 同步 strip 钩子设计正确，但 `updatedAt` 整行合并会让本地 LLM Key 被对端清空**
`ed43a62` 给 `wordSettings` 加了 `strip: ['llmApiKey', 'llmBase']`（导出前剔除，本机保留），提交注释明确写「对端导入后保留自己的本地 Key」。但 `sync-manifest.js` 的 `wordSettings` 用 `merge: 'updatedAt'`，而 `mergeRows` 的 `updatedAt` 分支是**整行替换**（`m.set(x.id, incoming)`）：对端 wordSettings 行没有 key 字段（已被 strip），只要它的 `updatedAt >=` 本地，本地整行被替换 → **`llmApiKey` 被覆盖成 undefined**，用户每次跨设备同步设置页后都要重新填 Key。strip 钩子只防了「泄露」，没防「覆盖」。
修复：`mergeRows` 对带 `strip` 的表改为字段级保留——合并结果中 strip 字段取本地值（`if (srs && srs[f] !== undefined)` 同款写法），或在 wordSettings 单行场景下 `out.llmApiKey = local.llmApiKey ?? incoming.llmApiKey`。建议给 `sync-manifest.test.mjs` 补一条「带 strip 的表跨端合并保留本地敏感字段」回归。

### P2（4 项）

**N-6（N-5 残留）`embeddings.sourceId` 未被重定向**
N-5 的 `CARD_REF_FIELDS = ['cardId', 'fromCardId', 'toCardId']` 覆盖 reviews/graphEdges/cardGroupLinks，但卡片的向量索引用的是 `embeddings.sourceId`（`agent/retrieval.js:indexCard`，`sourceType:'card'`），embeddings 表在同步清单内（`idOnly` 幂等）。被去重跳过的重复卡若已被 AI 索引，其 embedding 行仍带旧 `sourceId` 进合并 → 孤儿向量（不报错，但检索时 `cardIds` 回查拿到不存在的卡 id，静默多一次无效 join）。字段名不同导致通用遍历漏掉，正是 N-5 想消灭的「逐个枚举」问题的变体——建议把重定向字段表扩成 `['cardId','fromCardId','toCardId','sourceId']` 并加一条 embeddings 回归。

**P2-A i18n 闸门红且未挂进 npm 脚本**
`node scripts/check-view-i18n.mjs` 正向：**`t('views.wordBook.kind')` 在 zh 字典缺失**（WordBook.vue，英文界面该处直接显示 key 原文）；`--strict` 反向 **20 处新增**，集中在单词模块：`WordExport.vue` CSV/Excel 表头中文硬编码（英文 locale 导出的文件仍是中文表头）、`WordReview.vue:131` `（无例句）` 占位符、`WordSettings.vue:64` `保存失败：` toast、`WordBook.vue` subject 下拉 6 个选项 label 走 t() 但 `value="考研"` 中文值落库（数据层 localized 值，同 N-1 一类，切英文后导出/筛选显示中文类别）。
**根因是流程**：`package.json` 的 `test` / `build` / `pretest` 均未调用闸门（grep 无命中），前两轮全绿靠人工跑——`888544b` 与 `ed43a62` 两个大提交带红入库没人拦住。建议 `pretest` 挂正向 + `--js`（当前基线 0 新增，挂了即绿），`--strict` 作为独立 `check:i18n` 脚本。

**P2-B 全局搜索 / 学习统计 / 成就体系都不覆盖单词模块**
- `search/search-service.js` 的 `SCOPE_ORDER` 8 个 scope（cards/docs/mindmaps/memos/exams/notes/plans/analysis）没有 wordCards——4956 词的模块在全局搜索里完全不可达；
- `agent/analytics.js` 全部读 `db.reviews` / `db.cards`，单词复习记录（`db.wordReviews`）独立成表后，仪表盘、周报、体检、成就统计都不含背单词行为；
- 成就触发器无单词维度（wordCheckins 已建表有签到数据，成就却消费不到）。
单项都不致命，但「模块独立表」的隔离收益（不污染卡片查询）用三处功能缺口付了代价——建议统一开一个「学习数据 union 视图」（cards+wordCards、reviews+wordReviews 合并读），搜索/统计/成就共用，一次改造三处受益。

**P2-C `wordReviews.grade` 与 `reviews.grade` 口径不一**
`reviewWord` 的 grade 是 `rating>=2?'easy':rating===1?'hard':'failed'`（单维三档字符串）；`repo.review` 走 `retrievalGrading`（多维，含 retrievalStrength/responseMs）。两表同为「复习记录」但 grade 语义不可比——P2-B 的 union 视图落地时若不做口径对齐，跨模块正确率/难度统计会混着两种尺子算。

## 2. 交叉分析亮点

- **strip 钩子是本轮唯一的新机制扩展**（`ed43a62`），设计方向正确（敏感字段只 strip 导出、本机保留），且与隐私 opt-in 体系（`PRIVACY_SYNC_TABLES`）一致；P1-C 说明「导出侧过滤」与「合并侧语义」必须成对设计——后续任何表加 strip 都应同步过一遍对应 merge 策略。
- **单词模块对既有体系的复用度很高**：调度复用 `scheduleReview`（含 level 归一化 / NaN 兜底 / FSRS 双路径）、复习不 bump updatedAt（兼容双时间戳同步模型）、删除走快照+墓碑双写、`LIVENESS_FIELDS` 已含 `addedAt`（wordGroupLinks 增量包/墓碑复活判定不受影响）——这些「老坑」新模块都绕开了，质量明显高于早期模块。
- **并行提交频繁**：本次审计 6 小时内出现 3 个功能提交 + 1 个未提交批次（`888544b`、`ed43a62` 均为审计中途入库，WorkBuddy 并行作业），审计基线持续漂移。round12.md 在 `f37952a` 入库时已占用编号，本报告顺延 round13。
