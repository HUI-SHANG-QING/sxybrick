## 二、问题清单

### P2-1：同步拉取全量（上传增量 / 下载全量不对称）——图片数据量线性拖慢每次同步

**现象**：手动同步一次，手机要下载**整个数据文件**（含全部图片的 base64），图片越多越慢、流量越大。

**证据链**：
1. **推送侧是增量的**：`sync.js:179 buildIncrementalBackup` 只带 `updatedAt > since` 的变更行 + 被引用图片（round17 P3-3），注释明示「增量同步：只导出 updatedAt > lastSyncAt 的行……hub 端可据此识别」。
2. **但 hub 合并后返回全量**：`hub.js:728` `return json(req, res, 200, { ..., ...merged })`——`merged` 是**整份中枢数据文件**（所有表所有行，含所有图片 base64）。
3. **前端全量落库**：`sync.js:666` `importBackup(merged, ...)` 全量合并（无 since 水位过滤）——每次同步全量解析 + 全量写库。

**影响量化**（大白话）：
- 300 张图 × 平均 150KB ≈ 45MB 原始图 → base64 膨胀 33% ≈ **60MB 每次同步下载**；
- 图片持续增长 → 同步耗时与流量**线性上升**，且 `JSON.parse` 大字符串 + `bulkPut` 全量写库都占主线程；
- 中枢侧 `hub-data.json` 也随图片全量膨胀（每次 PUT 都 load→merge→save 整文件）。

**根因**：round17 只优化了「上传」单向；「下载」依赖 hub 返回权威全量来保证一致性（mergeRows 幂等、任何本地缺失自动补全），**没有利用 PUT 包里的 since 字段做对称优化**——增量拉取被设计意图预留（注释「hub 端可据此识别」）却未实现。

**修复方向**（按影响÷成本排序）：
- **方案 A（低成本，推荐）**：hub 响应中**图片按客户端 since 剪裁**——`collectPackImageIds` 同口径，只回「客户端 since 之后变更行引用的图片」；图片是体积大头，这一刀就砍掉 90%+ 的流量。行数据全量回传仍可接受（文本行 MB 级）。
- **方案 B（中成本）**：hub 维护表级水位，PUT 时算出「自客户端 since 以来变更的行 + 墓碑 + 引用图」回增量；客户端 importBackup 已有幂等合并，安全。需要 hub 侧 diff 或行级 since 过滤。
- **安全前提已具备**：墓碑始终全量带（round17 设计）、合并幂等（mergeRows）、时钟偏移换算（round30 P2-3）——增量拉取**不会引入正确性风险**。

## 三、根因分析（交叉思考）

1. **增量优化的「半程工程」**：round17 把「上传」做成增量，但「下载」停在全量——增量水位、墓碑全量带、合并幂等等**基础设施已经齐了**，只差 hub 响应侧的一层剪裁。这是「性能不对称」而非「正确性缺陷」。
2. **全量拉取的隐性代价被 LAN 掩盖**：局域网 RTT 低、带宽高，全量下载在测试期不痛不痒；一旦数据量涨到百 MB 级（图片是主因），或换成 4G/5G 弱网，每次同步的体感就会爆发。
3. **其余 7 个域零新发现**的正面结论：历轮 43~75 的修复（fieldTs 写入侧 diff、realReviews 统一过滤、缓存 key 自愈、hub 防御纵深）**不是补丁堆砌，而是形成了可验证的约定**——本轮交叉验证（fieldTs 完整性、quick 过滤、缓存失效、hub 鉴权）全部按约定生效。
