## 1. P1（数据错误 / 跨设备数据丢失，2 项）

### R17-1 番茄专注时长三处口径错位 → 每日实况/协同雷达「专注分钟」恒为 0
- **位置**：`src/repo.js:1047`（写端）／ `src/utils/planSynergy.js:103,106`（读端）
- **代码**：写端 `duration: Number(payload?.duration) || 0 // 分钟`；读端 `base.minutes = Math.round(rows.reduce((s,x) => s + (x?.durationMs || 0), 0) / 60000)`。
- **根因**：字段名（`duration` vs `durationMs`）与单位（分钟 vs 毫秒）双重错位。`pomoSessions` 从不写 `durationMs`，读端恒取 `0`。同一数据的第三处口径（`analytics.js:144`）却正确用 `x.duration`——三处各写各的。
- **影响**：`getDailyReality` 的「专注分钟」、每日协同雷达图「专注维度」、`totals.focusMinutes` 全部恒 0；用户看到的专注统计是空壳。
- **修复**：读端统一改 `x.duration`（分钟），去掉 `/60000`；或在写端同时落 `durationMs` 并全链路统一（推荐前者，改一处）。

### R17-2 复习记录「错题反思」跨设备同步实际从不落库（mergeRows 原地改引用）
- **位置**：`src/sync-manifest.js:201-205` ＋ `src/sync.js:552-556`
- **代码**：review 合并分支 `cur.selfExplanation = x.selfExplanation; ... m.set(x.id, cur)`——`cur` 来自 `new Map((base||[]).map(x=>[x.id,x]))`，与 `base`（`db.reviews.toArray()` 的结果）**同一对象引用**。随后 importBackup 用 `if (JSON.stringify(old) !== JSON.stringify(row))` 判定是否写库，而 `old === row`（同引用）→ 差异恒为 0 → **该行永远不进 toWrite**。
- **根因**：review 策略的「主体 idOnly + selfExplanation 字段级合并」在 hub 侧（整包保存 data 对象）生效，但客户端 import 依赖 JSON 差异检测决定落库，原地变更使差异恒 0。
- **影响**：设备 B 在设备 A 已存在的复习记录上补写的 `selfExplanation/selfExplainAt`，导入后**只在内存**、从不持久化；`wordReviews` 同受影响（同一策略）。跨设备错题反思 = 全部丢失，且回归测试从未覆盖「客户端导入合并反思」路径（hub 侧正常掩盖了客户端异常）。
- **修复**：先浅拷贝再合并：`const next = { ...cur }; if (x.selfExplanation !== undefined && (x.selfExplainAt??0) >= (next.selfExplainAt??0)) { next.selfExplanation = x.selfExplanation; if (x.selfExplainAt) next.selfExplainAt = x.selfExplainAt; } m.set(x.id, next);`。补回归：客户端 importBackup 后 `db.reviews.get(id).selfExplanation` 断言。

## 2. P2（逻辑缺陷 / 一致性缺陷，10 项）

### R17-3 每日协同雷达「评分分布」恒空：grade 语义升级后下游仍按数字比较
- **位置**：`src/utils/planSynergy.js:93-94` vs `src/repo.js:495`
- **代码**：`const g = r.grade ?? r.rating ?? r.level; if (g === 0 || g === 1 || g === 2) base.byGrade[g]++;`——round13 P2-C 后 `grade` 是字符串 `'failed'/'hard'/'medium'/'easy'`，`??` 短路使 `g` 恒为字符串，`===0/1/2` 恒 false → `byGrade` 恒空（旧无 grade 字段的历史记录才走 `r.rating` 兜底）。
- **修复**：字符串→数字映射（failed/hard→0, medium→1, easy→2）或直接用 `r.rating`。

### R17-4 协同「科目维度」失真：reviews 从不写 subject，全部落「未分类」
- **位置**：`src/utils/planSynergy.js:91` vs `src/repo.js:489-496`
- **代码**：`const subj = r.subject || '未分类';`——reviews 落库字段为 `{id,cardId,reviewedAt,rating,predR,...,grade,gradeScore}`，**无 subject**，只有 cardId。聚合层不 join 卡片表 → 所有复习按「未分类」分组，雷达图/按科统计恒失真。
- **修复**：聚合时 `cardId` join `db.cards` 取 subject；或写库时冗余 subject（推荐 join，避免冗余漂移）。

### R17-5 单词侧蒙对/检索强度信号链路仍是死代码（round16 只通了管道）
- **位置**：`src/word-repo.js:44`（`scheduleReview(card, rating, 1, false, …)` 硬编码 `guessed=false`）＋ `src/views/WordReview.vue:180`（`reviewWord(c.id, rating)` 不传任何 opts）
- **根因**：round16 R16-3 在 word-repo 侧留了 `retrievalStrength` 参数位并透传，但**唯一生产调用方从不传**——单词侧「蒙对降档」「recognize×0.7」「explain×1.5」对调度**全部无效**。R16-3 修的是管道，上游未接线。
- **修复**：WordReview 评分时采集 `guessed`（蒙对标记）与 `retrievalStrength`（如按作答时长/答题方式推导）传入 `reviewWord(c.id, rating, { guessed, retrievalStrength })`。这是功能接线，不是纯缺陷修复，需 UI 设计配合。

### R17-6 双调度器共用 `fsrs.last`，SM-2 期间不推进 → 切回 FSRS 间隔异常放大
- **位置**：`src/repo.js:488`（`fsrs: next.fsrs ?? card.fsrs`）＋ `src/srs.js` computeNext（SM-2 路径不返回 fsrs）＋ `src/fsrs.js:176`（`elapsedDays = (now - prev.last)/DAY`）
- **根因**：注释声称「切换调度器后可无缝接续」，但 SM-2 分支从不更新 `card.fsrs.last`。用户用 SM-2 复习 N 天后切回 FSRS，`elapsedDays` 横跨整个 SM-2 期 → 预测 R≈0 → `stabilityAfterRecall` 的 `(e^(w9(1−R))−1)` 被异常放大（≈e^1.046−1≈1.85×），间隔系统性虚高。
- **修复**：SM-2 分支也把 `fsrs.last` 推进到本次 `nowTs`（`fsrs: card.fsrs ? { ...card.fsrs, last: nowTs } : undefined`）。

### R17-7 检索强度乘子无上界，可旁路 FSRS/SM-2 的 365 天上限
- **位置**：`src/srs.js:232-233`
- **代码**：`r.intervalDays = Math.max(10/1440, r.intervalDays * RETRIEVAL_FACTOR[rs]); r.dueAt = ...`——只保下界不截上界；`explain`(×1.5) 可把 365 天硬上限推到 547.5 天，`nextInterval`/`MAX_STABILITY=365` 的封顶被旁路。
- **修复**：乘子后 `Math.min(365, r.intervalDays)` 并同步重算 dueAt。

### R17-8 idRemap 重定向漏 `sourceCardId` 与 cards 表自身 → 变式卡血缘断裂
- **位置**：`src/sync.js:472,481` vs `src/repo.js:140`
- **代码**：`CARD_REF_FIELDS = ['cardId','fromCardId','toCardId','sourceId']`（无 `sourceCardId`）；且 `if (key === 'cards' || ...) continue;` 把 cards 表自身排除。卡片有 `sourceCardId`（变式卡链），去重跳过卡后保留卡的 `sourceCardId` 仍指向已不存在的被跳卡 id。
- **修复**：`sourceCardId` 加入 CARD_REF_FIELDS；允许对 `backup.cards` 做单字段重定向（不整行替换）。

### R17-9 wordCards 复用 cards 形状的字段级合并 → AI 扩展字段整行丢失
- **位置**：`src/sync-manifest.js:85,118`（wordCards 用 `merge:'card'` ＋ `CARD_CONTENT_FIELDS = ['front','back',...]`）＋ `src/word-repo.js:142-206`
- **根因**：wordCards 无 `front/back`，但合并策略按 cards 字段名设计；`mergeCardPair` 的 `out={...content}` 是整行复制，v26 扩展字段（pos/defs/examples/mnemonics/audio 等）既不在 CONTENT 也不在 SRS 分组，**完全跟随「内容赢家」**。旧版形状较简的设备 bump updatedAt 后即成内容赢家 → 对端更全的 AI 扩展字段被整行覆盖丢失。
- **修复**：为 wordCards 定义 `WORD_CONTENT_FIELDS/WORD_EXT_FIELDS`，扩展字段按 updatedAt 字段级保护（或「字段并集」策略）。

### R17-10 `deleteDailyPlan` 非事务（兄弟函数 createDailyPlan 已事务化）
- **位置**：`src/repo.js:770-775`
- **代码**：`await db.dailyPlans.delete(planId); await cascadeDeletePlanTasks(planId, t); await db.tombstones.put(...)` 三步裸写无事务，`cascadeDeletePlanTasks`（:761-767）也无事务。中途异常 → 计划没了但任务/墓碑残留；墓碑缺失 → 对端把已删任务推回。
- **修复**：与 `deleteDailyTask` 一致，整体包 `db.transaction('rw', db.dailyPlans, db.dailyTasks, db.tombstones, ...)`。

### R17-11 「日期 key」两套格式（无补零 vs 补零）——建模层漂移代表
- **位置**：`src/utils/streak.js:9-12`（`${y}-${m}-${d}` 无补零）vs `src/word-repo.js:450-455`（`todayStr` 补零）
- **影响**：同一概念两种格式（`2026-9-1` vs `2026-09-01`），当前两模块各自独立不自错；任何跨模块合并统计/统一日历组件立即产生一天/一整月错位。
- **修复**：抽公共 `dateKey(ts)`（统一补零）全库替换（`streak.js`、`word-repo.js`、`getDailyCounts`）。

### R17-12 清空水位不随 hub/对端传播 → 「撤销监控」跨设备失效
- **位置**：`src/views/Export.vue:142,153`（写 localStorage）＋ `src/sync.js:532-535`（仅本机过滤）＋ `src/sync-hub/hub.js:146-155`（hub merge 无水位概念）
- **根因**：`clearedBefore` 水位是「每表每设备」的 O(1) 删除语义，但 hub 是共享汇合点。A 机清空 userOps 后，历史行仍在中枢数据文件；B 机（水位=0）拉取全量回灌并再次 PUT 推回 hub，「撤销监控」删除语义不粘、跨设备泄漏。
- **修复**：hub 侧为 userOps/privacyRecords 维护 `clearedBefore` 水位并在 merge/GET 过滤；或清空时写一条表级水位墓碑让 hub 消费。

## 4. 交叉分析

### 4.1 根因模式（跨发现共性）
1. **字段语义升级未同步下游**：R17-3（grade 三档数字→四档字符串）与 R17-1（duration 分钟/毫秒）是同一模式——数据结构演进时聚合端未迁移，静默产出 0/空。建议在 schema 版本迁移（`db.js`）里对聚合消费端做「口径断言」回归。
2. **双写/复用导致口径漂移**：R17-4（reviews 不冗余 subject）、R17-11（两套日期 key）、R17-9（wordCards 复用 cards 合并策略）——建模层缺少「每张表的字段契约」，复用默认策略时扩展字段裸奔。
3. **删除语义两套表达竞态**：R17-13（墓碑复活 vs 级联删）、R17-12（水位 vs hub）——墓碑/水位/级联删三机制对同一行叠加时互踩。建议统一删除传播路径（`tombstoneTable()` helper + 删除前先墓碑判定）。
