# round133 修复：AI 助手把工具调用标签当回答显示（DSML 泄漏）

> 依据：用户提供的真实对话记录（同一句「最新的卡片内容是什么」连续触发 6 次空转、
> 屏幕上出现 `<｜｜DSML｜｜ …>` 一堆标签）。

---

## 一、根因（三段，与用户看到的现象一一对应）

```
模型输出 <｜｜DSML｜｜ …>            ← 服务商侧训练出的工具调用格式（项目内 grep DSML 零匹配）
        ↓
parseToolCall() 只匹配 <tool>/<args>  ← 不匹配 → 返回 null
        ↓
工具【没有被执行】，但模型以为调过了
        ↓
parseFinal() 的「整段当回答」分支      ← base.js:91 旧实现
        ↓
原文原样返回 → 屏幕上出现乱码
        ↓
对话历史里存的就是这些标签 → 模型下一轮继续照抄 → 空转到步数耗尽
```

**证据**：项目文本协议是 `<tool>/<args>/<final>`（`base.js` 的 `PROTOCOL`），
全仓 `grep DSML` **零匹配** ⇒ DSML 不是本项目定义的格式，是模型侧输出。

**字符形态**（用用户原文逐字确认，未凭直觉猜）：分隔符 = **U+FF5C（`｜` 全角竖线）×2**；
`invoke` / `calls` 是正常开闭标签，**`parameter` 是自闭合**（无斜杠）：
`<｜｜DSML｜｜ parameter name="q" string="true">张宇<｜｜DSML｜｜ parameter>`

---

## 二、修复（三层，逐层加固）

### ① 入口兼容（根治）—— `parseToolCall` 增加 DSML 兜底
主协议没命中时再试 `parseDsmlToolCall()`：
- `invoke` 取工具名；`parameter` 逐个收集为 args；
- `string="false"` 的值按 **布尔 → 数字 → 原样** 还原
  （⚠️ 不用 `Number(val) || val` —— 那会吞掉显式 `0`，是项目明令禁止的写法）；
- **分隔符同时接受全角 `｜｜` 与半角 `||`**（不同服务商版本可能不同），关键字只认白名单三件套。

**效果**：工具真的会被执行 → 模型拿到工具观察 → 恢复正常问答，**不再是空转**。

### ② 出口过滤（治乱码的底线）—— `parseFinal`
- 文本里含 DSML → **返回 `null`**（它是工具调用，不是给用户的回答）
  ⇒ 上层走既有的「无 final」出口，**绝不会再把标签甩给用户**；
- 另加 `stripToolMarkup()`：剥掉残留的 `<tool>/<args>/<final>` 与截断的 DSML 尾巴。

**这一层即使将来出现第三种厂商格式，也能挡住「标签泄漏到屏幕」**。

### ③ 提示词预防 —— `PROTOCOL`
明确禁止改用 `<｜｜DSML｜｜>` / `<function_calls>` 等其它厂商格式。

## 四、诚实边界

1. **只修好了「格式不兼容」这一层**。若模型持续输出 DSML，它本身可能仍不如直接输出主协议
   得心应手；但**工具会真的被执行**、**屏幕上不会再出现乱码**，且模型看到工具观察后通常会切回主协议。
2. **未在真实模型上跑过端到端**（沙箱无 API 凭据）。验证是用**用户提供的真实文本样本**
   在函数级做的——覆盖了实际出现的全部形态（单参数 / 多参数 / 无参数 / 截断）。
3. 用户对话里「工具没返回结果」这句，**根因就是工具压根没执行**（格式不识别），
   已由 ① 解决；若修好后仍失败，那是另一条链路的问题，届时需按 `explainLlmFailure` 的口径排查。
4. 多 `invoke` 一次给多个工具时，本实现**只取第一个**（与主协议"每次仅一个"一致）；
   若将来要支持批量，需要先在协议层明确语义。
