## 2. 高严重性（4 项）

### H-1 算法 · desiredRetention=0 被静默覆盖为 0.9

- **位置**：`src/fsrs.js:156` `const desiredR = opts.desiredRetention || DEFAULT_DESIRED_RETENTION;`
- **成因**：JavaScript 的 `||` 对 `0`（falsy）回退到右侧。若调用方显式传 `desiredRetention: 0`（语义：不复习），实际被替换为 0.9（语义：高频率复习）——调度结果与调用方意图完全相反。
- **对照**：`src/algorithms/forecast.js:61` 使用 `opts.desiredRetention ?? DEFAULT_DESIRED_RETENTION`（正确）。同一代码库两种写法，说明这是疏漏而非设计。
- **影响范围**：所有经 `schedule()` 进入 FSRS 路径的调度。`desiredRetention: 0` 是极端边界，但 `??` 替换 `||` 是零成本防御，不应依赖"没人会这么传"。
- **触发条件**：任何调用 `schedule(card, rating, { desiredRetention: 0 })` 的路径。
- **修改方向**：`opts.desiredRetention ?? DEFAULT_DESIRED_RETENTION`。同理 `opts.weights ?? DEFAULT_WEIGHTS`、`opts.now ?? Date.now()` 也应用 `??`（当前 `opts.now ?? Date.now()` 已正确，仅 desiredRetention 漏了）。

### H-2 数据对象 · graphEdges 缺 fromCardId/toCardId 索引 → deleteCard 全表扫描

- **位置**：`src/db.js:50` `graphEdges: 'id, from, to, updatedAt'` + `src/repo.js:306,324` `db.graphEdges.filter(e => e.fromCardId === id || e.toCardId === id)`
- **成因**：schema 只给 `from`/`to` 建了索引（文本标签/UUID 混用），`fromCardId`/`toCardId`（卡片 UUID 引用）无索引。`deleteCard` 和 `importBackup` 的墓碑级联都用 `.filter()` 做全表扫描。
- **影响范围**：每张卡片删除时遍历全表 graphEdges（可能数千条）。`importBackup` 的卡片墓碑级联（`sync.js:671`）同样受影响。卡片数 >500 时 deleteCard 延迟可感知。
- **触发条件**：删除有图谱关联的卡片；同步时应用卡片墓碑。
- **修改方向**：db.js schema v25 新增 `fromCardId`/`toCardId` 索引（或复合索引），将 `filter()` 改为 `.where('fromCardId').equals(id)` + `.where('toCardId').equals(id)` 两次索引查询合并。

### H-3 数据对象 · pomoSessions 缺 partial 索引 → countPomoToday 内存过滤

- **位置**：`src/db.js:56` `pomoSessions: 'id, startedAt'` + `src/repo.js:1100-1103`
- **成因**：`countPomoToday` 先 `where('startedAt').aboveOrEqual(dayStart).toArray()` 取出今日全部 session，再 `.filter(isPomoCountable)` 内存过滤 partial 行。partial 是布尔标记，无索引意味着每次计数都扫描全量今日 session。
- **影响范围**：`countPomoToday` 被成就收集、 analytics、周报、Pomodoro 刷新等高频路径调用。日 session 数 <100 时影响微乎其微，但若用户高频使用番茄钟（含 partial 行），累积可感知。
- **触发条件**：每日番茄数 >50（含大量 partial 行）。
- **修改方向**：方案 A（低成本）：schema v25 加 `partial` 索引，`countPomoToday` 改为 `.where('startedAt').aboveOrEqual(dayStart).and(s => !s.partial).count()`。方案 B（零 schema 变更）：保持内存过滤，但将 `toArray()` 改为 `.filter().count()` 避免加载全量对象。

### H-4 业务逻辑 · importBackup 单事务锁全表 → 大包导入卡顿

- **位置**：`src/sync.js:585` `await db.transaction('rw', ...txTables, async () => { ... })`
- **成因**：整个 importBackup（墓碑合并 + 逐表 merge + 图片写入 + 墓碑级联 + 复活清理）包裹在单个 Dexie 事务中。Dexie 事务持有 IndexedDB 写锁直到完成。千卡级导入（>2000 卡 + 数万 review + 图片）可能耗时数秒，期间所有 IndexedDB 读写被阻塞。
- **影响范围**：同步拉取大包、Gist 备份恢复、Anki 大批量导入。移动端 IndexedDB 性能更差，阻塞更明显。
- **触发条件**：数据包 >5MB 或卡片 >2000 张。
- **修改方向**：分阶段事务：墓碑合并→提交（释放锁），各表 merge→提交，图片→提交。或改为流式处理：每 N 行一个子事务。需评估中断恢复语义（当前事务原子性是数据安全的保障）。

## 3. 中严重性（5 项）

### M-1 数据协同 · pomoDedup localStorage 与 IndexedDB 失同步

- **位置**：`src/utils/pomoDedup.js`（localStorage `sxy_pomo_recorded`）+ `src/repo.js`（IndexedDB `pomoSessions`）
- **成因**：去重记录存 localStorage，session 数据存 IndexedDB。用户清除浏览器数据时可能只清 IndexedDB 不清 localStorage（或反之），导致：① localStorage 被清 → 去重记录丢失 → 重启后双标签页同轮专注可再次双写；② IndexedDB 被清但 localStorage 残留 → 新 session 被旧去重记录误判为已入账 → 该记的番茄被跳过。
- **影响范围**：Pomodoro 双写防护失效（场景①）或番茄漏记（场景②）。
- **触发条件**：用户手动清除浏览器数据；浏览器隐私模式自动清理；存储配额超限 localStorage 被清。
- **修改方向**：将去重记录迁入 IndexedDB（与 pomoSessions 同库同事务），或在 `restore()` 时校验 localStorage 记录与 IndexedDB session 的一致性（ mismatch 则清空去重集）。

### M-2 数据协同 · BroadcastChannel 消息丢失 → 去重窗口存在竞态间隙

- **位置**：`src/views/Pomodoro.vue:144` `bc?.postMessage({ type: 'pomo-finish', at: Date.now(), rid })` + `:152` `markRoundRecorded(rid)`
- **成因**：`postMessage` 在 `addPomoSession` 之后、`markRoundRecorded` 之前执行。若标签页在 `postMessage` 后、`markRoundRecorded` 前被 kill（浏览器 OOM、用户强制关闭），消息已发出但本页未标记。对端收到消息会 `markRoundRecorded(rid)`，但如果对端也同时在结算同一轮（节流导致几乎同时触发），两端都可能在 `isRoundRecorded(rid)` 检查时返回 false（因为 localStorage 写入尚未完成）。
- **影响范围**：极端低概率双写（两端同时通过检查后都入库）。
- **触发条件**：两个标签页的 `finish()` 在极短时间窗口内同时触发 + 其中一个被 kill。
- **修改方向**：将 `markRoundRecorded(rid)` 移到 `addPomoSession` 之前（先标记后入库），利用 localStorage 的原子写入保证。或在 `addPomoSession` 内部做 roundId 去重（数据库层兜底）。

### M-3 数据协同 · getStaleDocs 分页偏差 → docFiles 可能被挤压

- **位置**：`src/agent/retrieval.js:131-141`
- **成因**：`db.docs.limit(limit * 2)` 和 `db.docFiles.limit(limit * 2)` 各取 limit*2 条，合并后去重。若 db.docs 返回满额（limit*2 条），docFiles 的行在合并排序中可能被截断到 limit 条以内。当用户有大量 AI 文档（db.docs）但少量资料库文件（docFiles）时，docFiles 可能永远不被索引。
- **影响范围**：资料库文件的向量索引重建可能遗漏（仅影响 rebuildIndex 后的增量补全，全量重建不受影响）。
- **触发条件**：db.docs 数量 >> db.docFiles 数量（如 100+ AI 文档 vs 5 个资料库文件）。
- **修改方向**：改为 interleaving 取样：先各取 limit 条，若总条数不足 2*limit 再补取另一侧。或改为 `docTotal = docs.length + files.length; perSide = Math.ceil(limit * 2 / 2)` 分配配额。

### M-4 数据对象 · cardGroupLinks 注释过期 → 开发者误解墓碑语义

- **位置**：`src/db.js:196` `// 删除即移出（无墓碑：移出操作按 updatedAt 谁新听谁合并）`
- **成因**：注释说 cardGroupLinks 无墓碑，但 `deleteCard`（repo.js:301-302）实际写了 `kind: 'groupLink'` 墓碑。注释与代码矛盾，后续开发者可能据此注释做出错误假设（如跳过墓碑清理）。
- **影响范围**：代码可维护性，不影响运行时。
- **触发条件**：开发者阅读 schema 注释做决策时。
- **修改方向**：更新 db.js 注释，明确 cardGroupLinks 已有墓碑（round15 P1 修复）。

### M-5 算法 · mistakeAttribution O(n²) 聚类 → 500+ 错题时性能退化

- **位置**：`src/algorithms/mistakeAttribution.js:76-84`
- **成因**：贪心单连接聚类对所有卡片对做余弦相似度比较，复杂度 O(n²)。n=500 时 125K 次比较，n=1000 时 500K 次。每次比较涉及词汇表大小的点积运算。
- **影响范围**：错题本概念聚类页面的加载时间。普通用户错题数 <100 无感知，但重度用户或导入大量错题后可能卡顿。
- **触发条件**：错题数 >500。
- **修改方向**：方案 A：LSH（局部敏感哈希）近似聚类，O(n) 平均。方案 B：按 subject 分桶后桶内聚类，降低单次比较规模。方案 C：限制最大输入数（如取最近 300 条），超出部分分批。

## 4. 低严重性（4 项）

### L-1 算法 · trainWeights 无进度指示 → 大数据集 UI 冻结

- **位置**：`src/fsrs.js:273-297`（训练主循环）
- **成因**：每次迭代计算 19×2=38 次 lossOf()，每次遍历全部 review 记录。默认 30 轮迭代，review 数 >5000 时可耗时数秒到数十秒，主线程阻塞。
- **影响范围**：FSRS 权重训练 UI。普通用户 review 数 <1000 无感知，但长期用户可能 >10K。
- **修改方向**：用 Web Worker 执行训练循环，或改用 mini-batch 梯度下降（每次迭代只采样部分 review）。

### L-2 数据协同 · trashItem 失败静默 → 删除不可逆

- **位置**：`src/repo.js:185-194`
- **成因**：`trashItem` try/catch 只 `console.warn`，不阻断删除流程。若存储配额满或 IndexedDB 异常，卡片被物理删除但无回收站快照，用户无法恢复。
- **影响范围**：删除卡片/单词后的恢复能力。
- **触发条件**：IndexedDB 存储配额接近上限；移动端 Safari 无痕模式。
- **修改方向**：在 storage estimate API 可用时检查剩余配额，不足时提前警告用户。或将 trashItem 失败升级为阻断（删除前必须先成功写入回收站）。

### L-3 业务逻辑 · Review.vue 无 AI 调用超时 → UI 可能无限挂起

- **位置**：`src/views/Review.vue`（AI 辅助相关调用路径）
- **成因**：LLM API 调用（如 AI 出题、智能解释）无显式超时。若网络异常或 API 无响应，Promise 永远 pending，用户只能刷新页面。
- **影响范围**：AI 辅助复习功能的用户体验。
- **触发条件**：网络中断；LLM API 超时；代理服务器无响应。
- **修改方向**：用 `AbortSignal.timeout(30000)` 包裹 fetch 调用，或在调用层加 `Promise.race` 30s 超时降级。

### L-4 数据对象 · embeddings 复合索引不匹配查询模式

- **位置**：`src/db.js:75` `embeddings: 'id, sourceType, sourceId, subject, updatedAt, modelSig'`
- **成因**：`deleteCard` 和 `importBackup` 的级联清理用 `where('sourceId').equals(id).and(e => e.sourceType === 'card')`，但索引是 `sourceType` 在前、`sourceId` 在后。Dexie（IndexedDB）的 compound 索引只能从左前缀开始查询，`where('sourceId')` 无法利用 `sourceType` 前缀，退化为全表扫描 + 内存过滤。
- **影响范围**：删卡时清理关联向量的速度。embeddings 表通常 <10K 行，影响微小。
- **触发条件**：embeddings 行数 >5000。
- **修改方向**：schema v25 调整索引顺序为 `sourceId, sourceType`（或新增 `sourceId` 单字段索引），让 `where('sourceId').equals(id)` 命中索引。

## 5. 可扩展功能点（非缺陷）

1. **FSRS 训练进度条**（L-1 衍生）：Web Worker 通信可顺便传递每轮 loss，UI 展示实时收敛曲线。
2. **graphEdges fromCardId/toCardId 索引**（H-2 衍生）：索引就位后，图谱查询可支持「某张卡片的所有关联边」的高效查询，为卡片详情页的「关联图谱」面板提供数据基础。
3. **pomoSessions partial 索引**（H-3 衍生）：索引就位后，成就系统可支持「今日有效番茄数」的实时显示（当前是按需计算）。
4. **importBackup 分阶段事务**（H-4 衍生）：拆分后可支持「部分导入」（如只导入卡片不导入复习），为选择性恢复提供基础。
