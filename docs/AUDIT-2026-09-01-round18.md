## 2. P1（数据错误 / 跨设备数据丢失，2 项）

### R18-1 单词卡 `note` 批注 / `audio` 自定义音频跨设备静默丢失（R17-9 的漏网子集）
- **位置**：`src/sync-manifest.js:40`（`WORD_EXT_FIELDS` 10 字段，**不含 `note`/`audio`**）vs `src/word-repo.js:108-110`（repo 层 `EXT_FIELDS` **含 `audio`**、note 走 :131/:210-212 `setWordNote` 并推进 updatedAt）
- **代码**：`mergeCardPair`（sync-manifest.js:163-172）`const content = incTs >= locTs ? incoming : local; const out = { ...content }`——内容赢家**整行**复制，仅 `CARD_SRS_FIELDS` 与 `extFields` 受字段级保护；`note`/`audio` 两者都不在。
- **根因**：设备 A 写批注/上传自定义音频（updatedAt_A 新）；设备 B 之后仅复习（`reviewWord` 刻意不 bump updatedAt、只推 reviewedAt——设计正确）→ B 的 reviewedAt 不覆盖内容维度，但 **A 若先复习再在 B 侧编辑、或两端 updatedAt 交错**时，内容赢家取 updatedAt 较新的一方，另一方较旧的整行（含 note/audio）被覆盖。核心问题：note/audio 本属「用户手工编辑的内容」，却既不在 CONTENT 分组也不在 EXT 并集，合并命运完全跟随「谁 updatedAt 新」。
- **影响**：跨设备批注/自定义发音音频静默回退，无任何提示。单词模块是 v25/v26 最活跃模块，note 使用频率高于卡片侧。
- **修复**：`note`、`audio` 加入 `WORD_EXT_FIELDS`（并集保护，任一端有值即保留、incoming 优先）——一行改动，与 R17-9 同机制。

### R18-2 Gist「云备份」通道实为 last-writer-wins 覆盖：多设备任一侧推送即抹掉云端他人变更
- **位置**：`src/utils/gistBackup.js:88-94`（PATCH `files: { [fname]: { content: JSON.stringify(全量) } }` 整体覆盖）＋ `src/views/Sync.vue:122-140`（`uploadToGist` 直接 `buildBackup()` 全量推送，**无 pull-merge-push**）
- **代码**：推送前不 `fetchGistBackup`、不 `importBackup` 合并，直接以本地全量覆盖云端文件。
- **根因**：hub 通道有增量水位 + 中枢合并，gist 通道是裸覆盖。设备 A 推送全量后，设备 B 用自己本地全量（不含 A 的增量）覆盖 gist → 云端 A 的新增丢失；B 下次拉取把本地也污染成缺 A 数据的状态。
- **影响**：UI 定位是「云备份」（sync.js:91 `gistTitle: 'GitHub Gist 云备份'`），但多设备共用一个 gist 时行为是覆盖而非备份聚合。单设备场景无害；多设备场景数据静默丢失且不可恢复（gist 历史版本除外）。
- **修复**：`uploadToGist` 前先 `fetchGistBackup` + `importBackup` 合并再推送（pull-merge-push，复用现有导入链路 ~20 行）；或 UI 明确声明「gist 为单向备份，多设备请各建各的 gist」。

## 3. P2（逻辑缺陷 / 一致性缺陷，5 项）

### R18-3 快照回滚：旧快照缺表键 → `|| []` 清空整表（英语单词 7 表在旧快照下被抹）
- **位置**：`src/sync.js:213-216`（restoreSnapshot `const rows = (snap.rows?.[t.table] || []); await db[t.table].clear(); if (rows.length) bulkPut(rows)`）
- **代码**：回滚对 `getEffectiveSyncTables()` 的每张表**无条件 clear** 再 bulkPut；快照中不存在的表键 → `|| []` → clear 后空库。
- **根因**：`saveSnapshot` 按生成时的表清单落 rows；v25 之前生成的快照（或旧版本备份导入的快照）不含 wordCards/wordReviews/wordGroups/wordGroupLinks/wordSettings/wordCheckins/wordSyllabusMeta 7 表键 → 回滚即整表清空。同理 embeddings/userOps/docFiles/notes/dailyPlans/dailyTasks/cardGroups/cardGroupLinks/analysisSessions/analysisMessages 等所有「快照生成后才新增的表」都中招。
- **影响**：用户用任意旧备份/旧快照回滚一次 → 新模块数据全灭，且 Sync.vue:62 确认框只提示「非图片数据被覆盖」，不提示「快照不含的新表将被清空」。
- **修复**：restoreSnapshot 跳过 `snap.rows` 中不存在的表键（`if (snap.rows && !(t.table in snap.rows)) continue;`），并在确认框列出将清空/不触及的模块。

### R18-4 快照回滚清空 `db.meta` 但只还原 `goal` 一个键：FSRS 训练权重/考试日/筛选偏好被抹
- **位置**：`src/sync.js:219-224`（事务含 `db.meta`，clear 后仅 `if (snap.rows?.goal != null) put goal`）＋ `saveSnapshot` :180 只存 `rows.goal`
- **代码**：`db.meta` 是「同步排除」表（不在 SYNC_TABLES，已核验），但回滚把它当普通表**整表 clear**，只回填 goal。
- **根因**：meta 中另有 `scheduler`/`fsrsWeights`/`fsrsInfo`（App.vue:242/259-260，**用户花算力训练出来的 FSRS 权重**）、`examAt`（CardInsight.vue）、`pretestStability`（repo.js:144）、`smartFilters`（Cards.vue:583）、`duelWrongs`（Review.vue）等本机设置，回滚后全部丢失且无快照可恢复。
- **影响**：任意一次回滚 = FSRS 个性化权重归零（调度退回默认权重）+ 考试窗口/智能筛选/易混加权清零。
- **修复**：saveSnapshot 完整存 `rows.meta = await db.meta.toArray()`，restore 时整体还原；或回滚不 clear meta 非同步键（只处理 goal）。

### R18-5 LLM Key 经 hub 中转灌给未配置设备（R17-20 只修了半程：strip 保护是「本地有值才保留」）
- **位置**：`src/sync-manifest.js:236-241`（mergeRows updatedAt 策略的 strip 分支：`if (cur[k] !== undefined) out[k] = cur[k]`——**本地有值才保留**，本地空则落 incoming 值）＋ `sync-hub/hub.js:154-156`（merge 对**新行** `m.set(x.id, x)` 原样入 hub，strip 字段不剔除）
- **代码**：设备 A 首次填 key → A 本地 wordSettings 行含 key → A 推送时 exportRows 已 strip（:24-34 剔除 llmApiKey/llmBase），但 hub 侧若收到**旧客户端**未 strip 的行（或 hub-data.json 中 R17-20 之前已驻留的明文），merge 新行分支原样存入；设备 B（本地 key 为空）拉取该行时 `cur[k] === undefined` → `out[k]` 保持 incoming 的 key。
- **根因**：strip 语义是「导出剔除 + 本地有值保护」，不是「字段永不出域」。新行无本地行可比对时，strip 字段照常流动。
- **影响**：LLM Key（付费凭证）扩散到未配置设备；A 清空本地 key 后 hub 旧值仍会回灌。
- **修复**：mergeRows 的 strip 分支改为「strip 字段**永远不采纳 incoming**（本地空则落 undefined）」——与导出侧同口径，两行改动；同时 hub merge 新行分支对带 strip 的表剔除 strip 字段（根治中转仓库）。

### R18-6 番茄钟「到点即满记」：运行中断（关页/切后台休眠）后回来按满 25 分钟结算，专注时长可刷
- **位置**：`src/views/Pomodoro.vue:105-128`（restore() `if (s.running && s.endTs)` 且 `remain <= 0` → 直接 `finish()`）＋ :79-93（finish() 无条件 `addPomoSession({ duration: 25, startedAt: focusStartedAt })`，`focusStartedAt = endTs - 固定25min`）
- **代码**：状态只持久化 `endTs`，不持久化真实开始时刻与净专注时长；restore 判定只问「到没到点」不问「实际专注了多久」。
- **根因**：开始专注 2 分钟 → 关标签页 → 数小时后回来，restore 发现 `remain <= 0` → finish() 记满 25 分钟 + 今日番茄 +1 + 成就 pomo_1/pomo_50 触发（achievements.js:18-19）+ R17-1 修复后的「专注分钟」统计同步虚增。
- **影响**：专注数据（刚被 R17-1 修活的数据源）可被无限刷；成就与每日实况失实。
- **修复**：状态持久化 `focusStartedAt`（首次 start 时刻）+ 暂停累计净时长；结算 `duration = Math.min(25, 净时长/60000)`，低于阈值（如 <20 分钟）不计完整番茄只记实际分钟。

### R18-7 同步状态面板遗漏英语单词 7 表：最活跃模块的同步失败不可见
- **位置**：`src/sync-status.js:18-27`（`MODULE_LABELS` 止于 analysisMessages，23 项）＋ :30-36（`MODULE_ORDER` 止于 userOps）
- **代码**：`getEffectiveSyncTables()` 含 wordCards/wordReviews/wordGroups/wordGroupLinks/wordSettings/wordCheckins/wordSyllabusMeta 7 表（已核验 SYNC_TABLES :42-107）；未登记表在面板 label 回退为裸表名（:121）并按字母序沉底（:130）。
- **根因**：v25/v26 新增单词表时未同步维护 sync-status 的两份手写清单（与 R17-32 手写 35 表清单漏 word 8 表**同一根因**：表清单手写、新增表无强制登记点）。
- **影响**：单词模块是 v25 后同步量最大的模块（每次背词都写 wordCards/wordReviews），其同步失败/待同步在状态面板不可见——代码自述「全覆盖」与实际不符。
- **修复**：`MODULE_LABELS`/`MODULE_ORDER` 改为从 `SYNC_TABLES` 动态生成 + 表名→中文 label 映射表兜底（新增表自动入面板，不再手写清单）。

## 6. 交叉分析

### 6.1 根因模式（跨发现共性，延续 round17 四模式并新增两条）
1. **「快照/清单」手写 vs 动态注册漂移**（R18-3/4/7 三连）：restoreSnapshot 的表遍历、saveSnapshot 的 meta 存储、sync-status 的两份手写清单——**凡是手维护的表清单都会漏新表**。round17 R17-32（clearTestData 手写 35 表漏 word 8 表）与本轮 R18-7 是同根因第二次复发。根治方向：以 `SYNC_TABLES`/`db.tables` 为唯一事实源，所有「按表遍历」逻辑动态生成（快照、状态面板、重置、测试清理）。
2. **覆盖语义 vs 合并语义的通道分叉**（R18-2/5）：hub 通道有水位+合并，gist 通道是裸覆盖，strip 是「导出剔除」而非「字段出域」——**同一份数据经不同通道传播时语义不一致**。敏感字段（key）与用户内容（note/audio）都在分叉处裸奔。
3. **「到点」≠「完成」的状态机简化**（R18-6）：番茄钟用 `endTs` 单字段表示整个专注过程，restore 无法区分「专注满 25 分钟」与「开了 2 分钟就关了」。状态持久化字段不足导致恢复语义退化。
4. **事件绑定缺失的「死函数」**（R18-8）：`onAfterPrint` 写好了、逻辑对，但 `afterprint` 监听从未挂上——**写完 handler 未接线**的静默死功能，与 round16「信号链路空心」同型（函数存在 ≠ 链路工作）。
5. **中断不原子**（R18-10/14）：导入循环逐卡入库无整体回滚、meta 读-改-写无事务——与 round17 R17-10/29（事务补齐）同根因，本轮在 UI 层（导入）与 meta 单键两处再现。

### 6.2 可拓展功能方向（非缺陷）
1. **gist 通道升级为真同步**（R18-2 修复后）：pull-merge-push 打通后，gist 即可作为「无自托管服务器」场景的同步通道（替代 hub），与现有增量备份共用 `importBackup`——零新协议成本。
2. **快照「时间旅行」UI**（R18-3/4 修复后）：回滚语义安全后，可做「快照对比视图」（两快照间新增/删除/修改卡片列表）——`diffRows` 纯函数在 sync-manifest 已有合并原语，增量成本低。
3. **专注数据 × 记忆曲线联合分析**（R18-6 修复后）：番茄净时长可信后，可出「单位专注时长的记忆巩固量」（专注分钟 vs 次日 predR 提升）——R17-1 修活的专注数据 + 已有的 review 历史，数据矿现成。
4. **导入结果「失败清单」通用组件**（R18-10/13 修复后）：Anki/分享码/apkg 三处导入的失败明细统一收口为「可展开失败列表 + 复制坏行」组件，一次实现三处复用。

### 6.3 可优化点（非 bug）
- `restoreSnapshot` 当前每表 `clear`+`bulkPut` 两趟；十万行表可改 `bulkDelete(旧主键) + bulkPut(新行)` 单事务内差量写（R18-3 修复时可顺带评估）。
- `parseAnkiLines` 的 `slice(0, 300)` 魔法数：300 上限无文档依据（R18-10 修复时一并提为具名常量 + UI 提示）。
- sync-status 的 `recordAllModulesOk` 在 gist 推送成功时按 `getEffectiveSyncTables()` 全模块记 ok（Sync.vue:142-144）——gist 实际只备份、不验证对端，状态语义与 hub 不一致，R18-7 修面板时可顺带区分「已备份/已同步」两态。
