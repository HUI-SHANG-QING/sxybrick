## 一、本轮的两个实测发现

### 1.1 修好 `armDbNotify` 的代价：写库慢 25.8%（上轮没量）

上轮我修好了"跨 tab 广播从未生效"，验证了**功能恢复**，但**没量它让写库变慢多少**。
本轮用两个独立 Dexie 实例对照（一个装钩子、一个不装），各 1000 次 `put`：

| 场景 | 1000 次 put 耗时 |
|---|---|
| 未装配（修复前那个"永不触发"的状态） | 128.6 ms |
| 已装配（修复后的真实行为） | 161.7 ms |
| **差异** | **+33.2 ms ⇒ 每次写约 +33 µs（相对 +25.8%）** |

另外：**批量写 1000 次 → 创建了 1000 次定时器**。
（150ms 的 trailing 节流压住的是"**广播次数**"，压不住"**定时器创建/销毁次数**"——
每次写都要 `clearTimeout` + `setTimeout` 一次。）

**判断**：绝对代价很小（导入 1000 张卡多花 33ms，用户无感），**当前不需要优化**。
但如果将来出现"上万条批量写"的场景（整库导入 / 大规模同步），可以考虑把节流改成
「窗口内只更新时间戳、不重建定时器」——我分析过该改法是安全的
（定时器触发时，此前发生的写都已完成），但**这属于会改语义的改动，不该顺手做**。

> 这条本身是个教训：**修复有隐性成本，不实测就不知道**。上轮我只报了"功能恢复"，
> 没报"写库变慢 25.8%"。

### 1.2 全仓「空 catch」扫描：50 处完全静默，其中一处就是上轮的案发现场

| 类别 | 数量 | 评价 |
|---|---|---|
| catch 里有真实处理逻辑 | 354 处 | 正常 |
| catch 里只有注释（交代了为什么可忽略） | 145 处 | 可接受 |
| **catch 完全为空 `{}`** | **50 处** | **可能掩盖真错误** |

**关键发现**：`db.js:444-445`
```js
try { armDbNotify(instances.real); } catch {}   // ← round125 的案发现场
try { armDbNotify(instances.test); } catch {}
```
上一轮我修了 `armDbNotify` 内部的 bug，**却把掩盖它的空 catch 原封不动留着**。
这意味着：将来它再出任何问题，仍会被静默吞掉。
**本轮已改**：抽出 `armSafely()`，失败时 `console.warn` 留痕（只 warn 不抛，因为该功能退化不影响本页使用）。

其余 49 处分布：`T.xxx()` 埋点调用（约 20 处，属**合理**——埋点不该影响业务，但建议补注释说明）、
`localStorage` 读写（隐私模式）、`URL.revokeObjectURL`、PWA 回调等。

**同时暴露一个"审计工具自身的坑"**：我的扫描脚本 v1 报了 **0 处**——
因为它只匹配「`catch {` 后换行」的形式，把项目里大量使用的**单行 `catch { … }`** 全排除了。
**这个"不合理��� 0"是唯一的报警信号**：如果我不怀疑，就会得出"项目没有空 catch"的错误结论。
已修正匹配逻辑后得到上面的真实数据（v1 教训写进了脚本注释）。

## 二、核心：为什么"每轮修复都会引出问题"

### 2.1 前 4 轮的实证表

| 轮次 | 修了什么 | 引入了什么 | 当时为什么没发现 |
|---|---|---|---|
| round122 | 首页统计快照在改排期写路径上失效 | 无新问题（但**同类发现 2 处**） | — |
| round123 | 删卡时批注/孤儿图的墓碑口径 | 无新问题（但**同类发现 3 处**） | — |
| **round124** | 预览性能：公式绕开安全检查 | **根号/箭头/下括号 4 类公式变纯文字** | **验证样本只覆盖"典型形态"** |
| round125 | 跨 tab 广播从未生效 | 无新问题（但**放大了订阅侧风险**，已逐个排查） | — |

**结论：4 轮里只有 1 轮真引入了问题。** 用户感知上的"每轮都出问题"，
一部分来自**每轮都靠审计兜底**（而不是靠修复流程本身），一部分来自我自己引入的那 1 次。

### 2.2 六个反复出现的机制

**机制 1：验证样本的"形态覆盖"不足**（round124 的根因，也是最值钱的一条）
- 我用 16 个公式做样本，**全是"文本型"**；
- 漏了 KaTeX 的**"SVG 绘制型"**（`\sqrt` 根号、`\overrightarrow` 箭头、`\underbrace` 下括号）；
- 对策：**枚举式验证** —— 改渲染/解析类代码前，先跑一遍"该库所有常用输出的形态"，把形态清单列全再逐个测；
  而不是"举几个典型例子"。
- 反面教材就在隔壁：并行会话写的 `tests/quick-check.test.mjs` 覆盖了
  `0 / null / 'bad' / undefined / 9min / 59min / 61min` 等 **9 个边界值** —— 比我写的样本更全。

**机制 2："局部正确"代替"全局一致"**（round123 的发现）
- 修 1 处墓碑 → 扫描发现同类 5 处、漏 3 处；
- 对策：**修完必扫同类**（已验证有效：round123、round122 都是靠这一步把同类补齐的）。

**机制 3：门禁的"覆盖假象"**（round122 的发现）
- `round57 契约⑥` 门禁当时是**绿的**，但它只扫 `src/repo.js` **一个文件**；
- 一句话：**绿灯只代表"我看到的那部分没问题"**；
- 对策：门禁自身的扫描范围要定期审（本轮已扩到全仓 `.js`/`.vue`）。

**机制 4：空 catch 把"必现错误"伪装成"环境差异"**（round125 的根因，隐藏最深）
- `armDbNotify` 内部 100% 必现的 API 误用，被 `catch {}` 吞掉；
- 注释还写着"个别环境不支持 hooks 时静默降级" —— **一个善意的注释，反而成了误导**；
- 对策：**关键路径的 catch 必须留痕**（warn / 计数器），并加门禁约束新增的空 catch。

**机制 5：修好一个"失效功能"会激活沉睡的代码路径**（round125 的连带风险）
- `armDbNotify` 修好后，4 个订阅方**从死代码变成活代码**；
- 对策：修失效机制时，**强制列出并逐个审计其所有下游消费者**（本轮已做：确认订阅释放、确认回调纯读）。

**机制 6：修复有隐性成本，不实测不知道**（本轮新发现）
- 写库 +33µs（+25.8%）、批量写创建 1000 次定时器；
- 对策：**性能类与基建类修复，必须同时量"收益"与"代价"**，只报收益是不完整的交付。

### 2.3 最需要警惕的一句话

审计是**补救**，不是**根治**。连续 4 轮都能挖出新问题，说明当前流程是
「**改 → 下一轮审计兜底 → 再改**」的循环。下面第五节才是能跳出循环的部分。

   它的作用是"给下一轮提供检查清单"，不是结论。

   唯一的代码改动是 `db.js` 两处 catch 加留痕。
