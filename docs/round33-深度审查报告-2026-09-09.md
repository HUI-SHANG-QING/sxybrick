## 一、P2（会导致错误结果、静默数据异常或明显性能退化）

### A 组 · 数据协同 / 同步

**A-1　删资料后「资料图谱边」残留成幽灵边，并跨设备回灌**
- 位置：`src/repo.js:1571-1572`（`deleteDoc` 级联）
  ```js
  for (const e of await db.graphEdges.where('from').equals(id).toArray()) edgeMap.set(e.id, e);
  for (const e of await db.graphEdges.where('to').equals(id).toArray()) edgeMap.set(e.id, e);
  ```
- 根因：资料边的 `from/to` 存的是**知识点名（label）**，资料标识在独立字段 `docId`（见 `src/repo.js:1502` 判重用时用 `e.docId === docId && e.to === to`）。`deleteDoc` 拿 `docId` 去匹配 `from/to`，**恒匹配不到**；且 schema 索引为 `id, from, to, fromCardId, toCardId, updatedAt`（`src/db.js:292`），`docId` 无索引。
- 影响：删除资料 → 其图谱边常驻本地并随同步推给对端（与该级联注释「幽灵边常驻并跨设备传播」的修复意图相反）；图谱/导图出现指向已删资料的悬空节点。
- 建议：级联改为 `db.graphEdges.filter(e => e.docId === id).toArray()`（与 `docs-lib`/`graph-resolve` 的资料边口径对齐）；若量大再考虑给 `docId` 加索引（v32）。

**A-2　删「单词卡」在导入端无链接级联 → 孤儿链接跨设备拉锯**
- 位置：`src/sync.js:841-849`（`importBackup` 墓碑应用）
  ```js
  if (t.kind === 'card') continue;          // 仅卡片有专门级联
  const { removed } = applyTombstones(await db[t.table].toArray(), tombstones, t.kind);
  ```
- 根因：删卡（`cards`）在上方做了 reviews/notes/links 等级联；`wordCard` 墓碑只删 `wordCards` 行本身，`cardWordLinks` / `wordGroupLinks` 中指向该词卡的链接不清理。`sweepOrphanRows`（`src/repo.js:639-649`）只清 `reviews`/`wordReviews`，不碰链接表。
- 影响：孤儿链接随同步在对端反复回传（对端无该词卡 → 界面出现悬空关联；链接表单调膨胀）。
- 建议：墓碑应用阶段对 `kind === 'wordCard'` 增加链接裁剪（参照 cards 级联），或把 `sweepOrphanRows` 扩展为「按 kind 清理关联表」的通用表。

**A-3　`wordSyllabusMeta` 合并策略错配为 `idOnly` → 元信息更新静默丢失**
- 位置：`src/sync-manifest.js:145`
  ```js
  { table: 'wordSyllabusMeta', kind: 'wordSyllabusMeta', merge: 'idOnly' },
  ```
- 根因：该表 id 固定 `'kaoyan2027'`，`idOnly` 分支「已存在即保留」（`sync-manifest.js:466`），先到者赢；同族的 `wordSettings` / `syllabusMeanings` 均为 `updatedAt`。
- 影响：两端各自加载不同版本大纲后，`wordCount`/`loadedAt`/`source` 的更新被静默丢弃，且因 id 相同**永不会再补传**，只能靠一次全量覆盖。
- 建议：改为 `merge: 'updatedAt'`（单行元数据语义与 `wordSettings` 一致）。

### B 组 · 算法与统计口径

**B-1（跨组主项）　quickCheck 污染仍未收口：读取端「第四波」漏网**
- 已修（写入端 + 部分读取端）：`realReviews/isRealReview`（`repo-core.js`）、`computeStats`、`prepareFsrsTrainingData`（`analytics.js:181`）、`calibration/fsrs/intelligence.failCount/buildReviewsByCard`。
- **仍未过滤**（实证）：
  - `src/repo-core.js:176` `rankWeakCards`：`for (const r of reviews) if (r.rating === 0) fail.set(...)` → 薄弱卡/错题标记被快检失败污染（`weakCards` 走这里）。
  - `src/agent/analytics.js:108 / 214 / 270 / 319 / 436 / 678 / 726`：`db.reviews.toArray()` 后直接使用 → 学习画像、易混对、遗忘风险、高频错题、雷达等全部含 quick。
- 影响：快检（自测，不进调度）的 `rating:0` 被当真实遗忘 → 卡片被误判薄弱、错题集误入、遗忘预警与自动计划被错误驱动；且同一指标在 Dashboard（已过滤）与这些模块（未过滤）**数字打架**。
- 建议：统一收敛到 `realReviews()`，并优先把 `rankWeakCards` 的入参约定为「已过滤」。

**B-2　FSRS 训练权重无上界 → 权重发散可把间隔锁死 365 天**
- 位置：`src/fsrs.js:313`（`Math.max(0.01, wi - rate*(grad[i]/gn))` 仅下界）、`src/fsrs.js:345`（`serializeUserWeights` 仅校验 `>= 0`）
- 根因：`w[7]/w[9]/w[11]/w[13]` 进入 `exp()`/`pow()` 项，训练若把 `w[7]` 推高，`stabilityAfterRecall`（:124）会把 `S` 钳到 `MAX_STABILITY=365`，`nextInterval` 恒返 365 天。
- 影响：概率低但后果严重——一旦发散，大量卡片间隔被锁一年，复习计划静默崩坏，且无 per-index 校验兜底。
- 建议：`trainWeights` 输出后按 per-index 合理区间钳制（至少对指数项维度），`serializeUserWeights` 增加上界校验。

### C 组 · 业务计数口径

**C-1　「今日完成 / 连击 / 计划进度 / 每日现实」四处仍把 quickCheck 计入**
- 位置：`src/utils/streak.js:20`（`getStreak` 全表 `toArray`）、`:32`（`getTodayCount`）、`src/utils/planSynergy.js:88`（`aggregateReviews`）、`src/intelligence.js:716`（`fetchTodayRows`）、`src/repo.js:1315`（`getDailyReality`）
- 根因：同为 B-1 的读取端漏网；`Review.vue:253` 的「今日完成」直接取 `getTodayCount()`。
- 影响：只做快检的日子被算作「活跃」（连击不断）、今日复习量与计划完成度虚高，与 Dashboard（已过滤）不一致。
- 建议：四处统一 `realReviews`；`getStreak` 顺带把 `toArray` 换成按 `reviewedAt` 索引的降序扫描（见 D-4）。

**C-2　Dashboard 首屏同一份数据被全表物化多次**
- 位置：`src/repo.js:1029`（`getStats` = `allCards()` + `db.reviews.toArray()`）、`:971`（`weakCards` 同样两套全表）、`:1022` 附近 `getReviewSuggestion`
- 影响：万卡量级下，每次进首页读两遍全表 cards + 全表 reviews（主线程阻塞 + 内存峰值）。
- 建议：首屏合并为一次 cards + 一次 reviews 读取（或一个 5s 共享缓存），`weakCards` 复用同一快照。

**C-3　worker 不可用时，易混对计算回退为 O(n²) 主线程冻结**
- 位置：`src/agent/analytics.js:268-`（`_getConfusablePairs` 内 `cards.toArray()` + `reviews.toArray()` + 双层配对），`getConfusablePairs` 在 `offload` 返回 `_FALLBACK` 时直接调用它
- 影响：CSP / `file://` / 老浏览器导致 module worker 不可用时，千卡级直接卡死主线程（无降级护栏）。
- 建议：fallback 加候选上限（如只对近 N 条错题、每卡最多比对 M 个候选）或分批次 + 让出主线程。

## 三、误报澄清（子代理提出但经核验不成立 / 属既有设计）

1. **「单模块同步导致其它模块拉不到数据」→ 不成立**：hub PUT 返回的是**全量 merged**（`sync-hub/hub.js:544` `...merged` 来自 `merge(loadScopedData(scope), incoming, skew)`），`importBackup` 会处理所有表；单表限制只作用于**推送侧**，符合「单模块同步」语义。相关风险仅剩 D-2（状态误报）。
2. **「回收站不跨设备同步」→ 既有决策**：删除语义由墓碑表达，回收站快照仅本机恢复用，开放同步会与墓碑复活判定冲突（已在 sync-manifest 注释固化）。
3. **「quickCheck 写入端污染」→ 已修**：`quickCheck.js:48` 写 `type:'quick'` 约定已在写入端与多个读取端收口；本轮只报**读取端残留**（B-1 / C-1）。
