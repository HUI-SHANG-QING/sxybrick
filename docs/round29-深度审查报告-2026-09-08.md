# SxyBrick 深度审查报告（2026-09-08，基于本轮实测修复经验）

## 一、审查方法：从已修缺陷反推模式

本轮我先修了 5 个用户实测缺陷，事后归纳发现它们**同源**：

| # | 现象 | 归类 |
|---|---|---|
| 1 | 检索失败、强刷无效、换浏览器好 | 同一语义**两处存储**，一处不落盘 |
| 2 | 红标只在手机显示 | **派生值**被当持久字段，且依赖本地开关 |
| 3 | 清缓存无效、无痕正常 | 持久化状态**恢复后不校验有效性** |
| 4 | 平板轻点设置闪退 | 靠**时间窗**做去重（时序假设） |
| 5 | 错题集里混合检索失效 | 模式分支 **early-return 绕过通用逻辑** |

**统一模式：同一份语义在多处实现 / 多处存储，其中一处漏了。** 本次审查即按这五类模式反向全项目扫描，再叠加算法边界、性能、数据建模三个维度。

## 三、P0 详解：卡片合并其实是整行 LWW

```js
// sync-manifest.js:214-216
const content = incTs > locTs ? incoming : (locTs > incTs ? local : (tiebreak(...) ? incoming : local));
const out = { ...content, updatedAt: Math.max(incTs, locTs) };   // ← 整个赢家行展开
for (const f of CARD_SRS_FIELDS) { ... }                          // 只有 SRS 组是逐字段的
```

文件顶部注释与 `sync-manifest.js:8-9` 承诺"内容字段按 `updatedAt`、SRS 字段按 `reviewedAt` **字段级合并**"，但内容组从未参与——`CARD_CONTENT_FIELDS` 全项目只出现在定义处和冲突展示 (`sync.js:1012`)。

**后果**：设备 A 改 `front`（updatedAt=T1），设备 B 改 `back`（updatedAt=T2>T1），同步后 B 整行胜出——**A 的 front 修改静默丢失**。多端编辑场景下这是真实的数据丢失，且极难复现与察觉。

**三个改进选项**（风险递增，需你拍板）：

| 选项 | 做法 | 代价 | 解决程度 |
|---|---|---|---|
| A | 修正注释与文档，明确"内容整行 LWW"语义 | 极低 | 消除误导，不解决问题 |
| B | 对易丢的**派生/状态字段**引入独立时间戳（`linkedNoteIdsAt`、`familiarAt`、`quickCheckedAt`），写入侧 bump | 中 | 解决状态回退，不解决 front/back 互覆盖 |
| C | 卡片引入**字段级时间戳** `fieldTs: { front: ts, back: ts, ... }`，合并时逐字段比较 | 高（写入侧全改 + 迁移） | 彻底实现宣称的语义 |

我的建议：先做 **A + B**（B 覆盖最容易丢的几项），C 列为技术债并设计迁移方案。

## 五、架构层面的三条建议

1. **派生值不入库**：像 `failCount` 这类由流水聚合的值，统一走 `attach*` 入口在数据出口注入，不要在卡片行上持久化——持久了就必然参与整行 LWW（这正是 P0 与 P1 的交汇点）。
2. **持久化的 UI 状态必须"恢复即校验"**：任何从 localStorage 恢复的筛选/开关/位置，加载完真实数据后都要做一次存在性校验，无效就丢弃。这是本次 5 个缺陷里占了 3 个的模式。
3. **别用时间窗做正确性判定**：600ms 去重这类写法应改成"本次序列是否已处理"的标志位；时间窗只在设备/负载变化时随机失效，测不出来。
