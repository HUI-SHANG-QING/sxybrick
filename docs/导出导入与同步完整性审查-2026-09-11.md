## 一、权威覆盖口径（47 张表全部有归属）

`node scripts/sync-coverage-audit.mjs` 实测：**db 表 47｜同步 33｜隐私 opt-in 1｜显式排除 11**（另有 2 个特殊通道）= 47，零漏登记。

### 1) 随包走的 33 张同步表
cards / reviews / images / aiChats / aiMemories / memos / plans / graphEdges / docs / pomoSessions / mindmaps / weeklyReports / achievements / exams / embeddings / userOps / docFiles / notes / dailyPlans / dailyTasks / cardGroups / cardGroupLinks / cardWordLinks / analysisSessions / analysisMessages / wordCards / wordReviews / wordGroups / wordGroupLinks / wordSettings / wordCheckins / wordSyllabusMeta / syllabusMeanings

- graphEdges 有一处**导出侧过滤**：`kind==='auto'` 的自动推导边**不进包**（派生数据，各设备自行重算；进包会「越同步越乱」）。
- wordSettings 有 **strip 钩子**：`llmApiKey / llmBase` 导出/合并/中枢三处统一剔除，本机凭证永不出域。

### 2) 特殊通道 2 个
| 通道 | 内容 |
|---|---|
| `tombstones` | 删除语义，**全量随包**（删除必须能跨设备传播） |
| `meta` | 打包为 `streakMeta`/`examMeta`/`schedMeta`，覆盖 6 个键：`goal`(打卡目标)、`examAt`(考试日期)、`scheduler`、`fsrsWeights`、`fsrsInfo`、`pretestStability`（后 4 个为 round37 补齐，防换设备后调度系统性分叉） |

### 3) 显式排除（11 张，均"本机专属/派生/跨设备无意义"）
| 表 | 不导出原因 | 对用户的实际影响 |
|---|---|---|
| docTexts | 资料解析全文（大字段） | **新设备只看到资料清单，不能预览/检索原文** |
| docBlobs | OPFS 降级暂存的原文件二进制 | **新设备不能打开原文件**（需重新上传） |
| trash | 回收站快照（删除语义由墓碑表达） | 新设备看不到回收站内容（也不需要） |
| snapshots | 本机回滚快照 | 快照仅本机可回滚 |
| plugins | 插件 + 配置（可能含 API Key） | 插件需在新设备重装（安全考虑） |
| notifications / errors | 本机提示/错误日志 | 无影响 |
| aiUsage | 本机 AI 用量账本 | 用量不跨设备（避免虚增） |
| wordExportHistory | 英语导出历史 | 无影响 |
| wordStudyLog | 英语学习时长流水 | 不跨设备相加（避免时长虚增） |
| imageRefs | 图片反向索引（派生表，可重建） | 无影响（可 rebuildImageRefs 重建） |

### 4) 隐私表 privacyRecords
默认**完全不进包**；仅当用户在设置里显式开启「隐私同步」后，才加入有效同步清单（PIPL 合规）。

### 5) 图片
- 图片以 base64 随包（`images: [{id, mime, data}]`），但**只收集被卡片 front/back 引用的图**。
- 实测**全项目唯一图片写入口是 CardModal（卡片编辑器）**（`putImage` 唯一调用方），笔记/资料编辑器没有插图入口 → 用户能创建的图片都被覆盖。
- ⚠️ **唯一边角**：一张卡被删除后，若某图片仅被笔记/资料正文以 `sxy-img://` 残留引用，则该图本机不删（GC 会扫笔记/资料）但**不随包走**。概率极低，建议加固（见第五节）。

## 二、Q1：导出功能是否"一次导出全部数据"？

**结论：是（在明确边界内）。** 「全量同步包」导出 = `buildBackup()`：
- 33 张同步表全量行（graphEdges 仅去掉 auto 派生边）；
- 被卡片引用的图片（base64）；
- 全量墓碑（保证新设备不会"复活"已删除内容）；
- 6 个元数据键；
- 隐私表仅在开启隐私同步时包含。

**不包含**（按设计）：资料库原文/全文（docBlobs/docTexts）、回收站、回滚快照、插件、本机诊断/用量/时长、隐私（需 opt-in）。
另有：加密备份（.sxybrick，AES-GCM+PBKDF2）内容范围同上，只是落盘加密。

> 结论要点：**不存在"被遗忘的隐藏表"**；存在的是"按产品设计不跨设备"的类别。最需要注意的是 **资料库原文/全文不导出**——这不是 bug，但用户容易误判为数据丢失，建议在导出页显式提示。

## 三、Q2：手动同步是否有"看不见的底层数据遗漏"？

**结论：没有遗漏，口径与全量导出一致。**
- 手动同步 `syncWithHub()` 一次 PUT：上行**增量包**（`buildIncrementalBackup`：本次变更行 + **全量墓碑** + 变更卡引用的图片 + 变更的元数据键）→ 中枢合并后回传合并结果 → 客户端 `importBackup(merged, {clockSkew, skipSnapshot})` 落库。
- 覆盖范围 = `getEffectiveSyncTables()`（同 SYNC_TABLES + 可选隐私表），排除清单同第二节。
- 独有增强：① 单模块同步（只推/拉某表）；② 时钟偏移补偿（HTTP `Date` 头换算对端时间到本机帧）；③ 中枢 GC 的墓碑回传（`gcTombIds`）消除本机墓碑无限膨胀；④ 20s 超时 + 混合内容/CORS 精准报错。

> 结论要点：47 张表全部有明确归属（33 同步 / 1 隐私 opt-in / 11 本地排除 / 2 特殊通道），**不存在"底层表静默不同步"**。唯一需要向用户交代的是"资料原文/全文、回收站、快照、插件不随同步"这一产品语义。

## 四、Q3：导入的完整性与处理逻辑

`importBackup()` 流程（按序）：
1. **版本门禁**：`backup.version > BACKUP_VERSION(8)` → 明确拒绝并提示升级（旧包 v≤8 仍可导入；低于当前属兼容）。
2. **自动快照**：默认先 `saveSnapshot('backup-before-import')` 可回滚；自动合并路径（hub 同步/Gist pull-merge）用 `skipSnapshot` 避免快照噪声（回滚手段=手动导出/导入）。
3. **内容去重**：异 id 同内容的**卡/词卡**合并为一张（保留本地），生成 `idRemap` → 重映射全部引用字段（sync-dedup 注册表）+ **重写正文 `[[c-]]/[[d-]]` 双向链接**，避免悬空。
4. **墓碑合并 + 应用**：按 `deletedAt` 合并；再应用到本地行（删除跨设备生效）。**"删除后又编辑"可复活**（行 `livenessTs > deletedAt`）。
5. **按表策略合并**：`card`（卡片专属）/`updatedAt`/`review`/`chat`/`idOnly`（见第五节）。
6. **图片**：base64→Blob，按 id **幂等**（已存在的跳过，不覆盖本地 Blob）。
7. **收尾**：孤儿复习行清扫、孤儿图 GC、损坏 dueAt 修复、埋点/AI用量/隐私记录按保留期裁剪、跨 tab 广播刷新。
8. **冲突可视化**：返回 `stats.conflicts`，逐条列出"被谁覆盖了哪些卡片字段"。

> 结论要点：导入是**"合并"而非"覆盖"**，幂等、可回滚、可重复执行；不会因为导入旧包而清掉本机更新的数据。

## 五、多设备冲突：系统已经比"整行最新覆盖"更精细

### 5.1 卡片合并模型（field-level，不是整行 LWW）
| 分组 | 合并依据 | 字段 |
|---|---|---|
| 内容侧 | **逐字段 fieldTs**（无 fieldTs 时回退整行 `updatedAt`） | front/back/subject/source/type/marked/mnemonic/tags/难度… |
| SRS 侧 | `reviewedAt` 谁新听谁 | ease/level/intervalDays/dueAt/consolidation/fsrs |
| 错因侧 | `wrongReasonAt` 独立时间戳（含"清空优先"） | wrongReason |
| 派生/状态 | 只要写入点 bump `fieldTs[f]` 即享逐字段保护 | quickCheckedAt/linkedNoteIds/词卡 kind·familiar… |

- **相同字段两端都改**：字段级 LWW，时间戳较新者胜；**时间戳相等**时按序列化字典序**确定性收敛**（两台设备收敛到同一结果，杜绝"A 认 B、B 认 A"来回横跳）。
- **时钟偏移**：用同步通道两侧时刻估算 `clockSkew`，把对端时间戳换算进本机帧再比较——防"快时钟设备用旧数据静默覆盖本机新编辑"。
- **对话 aiChats**：messages 做**并集**（对端独有新消息不丢）；词卡 AI 扩展字段做**并集保护**（不因形状简的设备提升 updatedAt 而覆盖掉更全的题目）。
- **删除**：墓碑 `deletedAt` 传播；本地行 `livenessTs > deletedAt` 视为"删除后又编辑"→ 复活并清除墓碑。

### 5.2 直接回答你的两个场景
**场景 A：手机改标题、平板改内容 → 不算冲突，两者都保留。**
标题与内容是**不同字段**，字段级合并各自取新，两边修改同时生效（这正是 round29 起专门修的目标）。

**场景 B：同一字段两端都改 → 算冲突，按该字段的时间戳较新者胜**（字段级 LWW，不是整行）。若时间戳恰好相等，按确定性规则收敛，两端最终一致。

### 5.3 关于"要不要加同步时间戳、最新覆盖"——你的方向对，但系统已做得更细
- **已有时间戳**，且不止一个：`updatedAt`（内容）+ `reviewedAt`（复习进度）+ `wrongReasonAt`（错因）+ **`fieldTs[字段]`（逐字段）**。
- **不是"整行最新覆盖"**：整行覆盖会把"手机刚改的标题"和"平板刚改的内容"二选一丢掉；逐字段合并让两者共存。
- **无需用户手动加时间戳**；唯一前提是设备时钟不要差太多（系统已用 HTTP `Date` 头自动补偿）。
- 冲突结果可在导入后从 `stats.conflicts` 看到（哪些字段被谁覆盖）。
