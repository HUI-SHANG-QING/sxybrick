## 一、总评（大白话）

这一轮不找新功能的问题，专门翻"看不见的底层"：表结构建得对不对、索引跟不跟得上查询、两台设备同步时会不会打架、算法状态机会不会算出鬼数字、缓存会不会把内存吃光。

**结论先说：底子很干净。** 五个角度横切下来，只在"聊天记录合并"这一个角落找到 1 个 P3（同毫秒并发时谁覆盖谁看运气），其余全部通过。round43/44 修的东西也一件没丢。

大白话总结每一块：

- **数据建模（表和索引）**：34 个版本的 schema 迭代没有欠账。全库 40 处数据库查询，每一处都有索引接着，没有一处是"翻全表找数据"；排序字段也全在索引里。相当于图书馆每本书都在目录里能查到，没有"凭记忆找书"的情况。
- **数据协同（同步与事务）**：删一张卡牵连 11 张表（复习记录、分组链接、图谱边、墓碑……），全部包在**一个事务**里——中途断电也不会留下一张"删了一半"的卡。字段级合并（两台设备分别改一张卡的正面和背面，两边都保留）写得对，平局时靠"两端重算得到同一结果"收敛，不依赖谁先谁后。唯一的漏网之鱼在聊天记录合并（见 N1）。
- **算法与业务逻辑**：FSRS 状态机的护栏非常全——非数字输入会兜底、稳定度封顶 365 天（不封顶的话错一次题会"反弹"出一个天文数字间隔）、梯度训练有双界钳制防发散。日期边界用"本地零点、左闭右开"的窗口，跨天统计不会重复也不会漏。SM2 老数据迁移进 FSRS 时有界钳制，不会带入异常值。
- **异常与性能**：全局有未捕获 Promise 兜底（main.js:97），单点出错不会白屏。四个模块级缓存（图片 blob、OCR 文本、插件模块、相对时间格式化）全部有上限或按需淘汰，长会话不会内存泄漏。AI 检索查向量用批量 `anyOf`，没有"查一条跑一趟数据库"的 N+1 问题。

## 三、本轮新发现

### N1 [P3] 聊天记录合并的同毫秒竞态：`mergeChatPair` 用 `it >= lt`，平局靠参数顺序碰运气

- **位置**：`sync-manifest.js:407` 附近——aiChats 的自定义合并里，标量字段（标题、模型名等）按"updatedAt 大者赢"，但比较用的是 `it >= lt`（大于**等于**也算 incoming 赢）。
- **问题**：两台设备在**同一毫秒**内改同一字段（updatedAt 相等）时，谁是 local 谁是 incoming 由同步时序决定——结果就是"谁覆盖谁看运气"。这**正是卡片侧早就修掉的同一类问题**：mergeCardPair 的字段级合并（round32 C4 之后）平局时改用确定性收敛（同值短路径 + 显式拷贝纪律），而 chat 侧的自定义合并没跟上这个口径。复习记录合并（`merge: 'review'`）已核实走的是确定性路径，不受影响。
- **实际影响**：极小——需要两台设备同毫秒写同一聊天会话的同一标量字段。即便触发，后果也只是"标题/模型名显示为另一端版本"，不丢消息内容（消息体是数组追加语义，不受 `>=` 影响）。
- **建议**：把 `it >= lt` 改成 `it > lt`（平局保持 local），或者像卡片侧一样平局时比较一个次级 tiebreaker（如消息数）。约 3 行。

### N2 [P3·备忘] `rtfCache`（相对时间格式化缓存）按语言标签增长，无上限但实际有界

- **位置**：`utils/locale-date.js:107`。键是 intlTag()（跟随界面语言），实际取值就那么几种（zh/en 等），换一次语言加一条，不会膨胀。
- **结论**：不修。记录在案只是因为本轮承诺"扫过所有模块级 Map/Set"，它属于"理论上无界、实践上有界"，与 images.js（LRU 300）、ocr-cache（LRU 200）、plugins/loader（同 id 释放旧 Blob）的处置不同——后三者是主动封顶的，这个靠业务自然封顶。
