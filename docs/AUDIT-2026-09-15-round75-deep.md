# round75：AI 对话为什么还在高频失败 —— 剩余的结构性原因

> 用户问：「为什么 AI 对话功能还存在高频失败现象」。
> 本轮把**代码侧还能造成高频失败的原因**找齐并修掉，同时给出「怎么判断你手上是不是旧版本」。

---

## 一、先分清两件事：旧版本的锅 vs 代码的锅

你贴的记录里，降级文案是这一句：

> ⚠️ **AI 合成回答暂不可用**（网络或服务异常）。以下是你本地数据的直接结果，未经模型改写。

**括号里只有一句笼统的「网络或服务异常」= round73 之前的旧文案**。round73 之后这里会写**具体原因**
（「模型响应超时，已改为本地直出」/「触发频率限制（429）」/「API 密钥无效或无权限」/「接口返回 HTTP 400…」）。
所以那些记录里的大部分失败，是**旧版本的已知缺陷**（工具结果用原生 `role:'tool'` 回灌 → 服务端 400 → 整段降级），
不是新版本仍在犯的错。

**怎么验证新版本是否生效**（部署后强刷一次）：
1. 再问一次「你能看到卡片详细内容吗」→ 新版本 Agent 应**直接给出回答**，不再出现 ⚠️ 降级块；
2. 万一还失败，文案里**必须带具体原因**；如果还是笼统的「网络或服务异常」，说明浏览器仍跑着旧缓存。

## 二、本轮找到并修掉的**代码侧**原因

### R1（最大的一块）：**完全没有重试** —— 429 / 5xx / 网络抖动一次就投降

`llm.js` 此前只在三种特殊情形下重试（模型不支持视觉、`max_tokens` 被拒、端点不支持 stream），
**对 429 限流、500~504 后端抖动、网络瞬时失败完全没有重试**：`fetch` 失败 → 直接抛 → 上层降级。

而一次问话的调用量并不小：

| 场景 | LLM 调用次数 |
| --- | --- |
| 单轮问答（学习答疑导师） | 1~4 次（ReAct：每调一次工具就多一次） |
| 多智能体流水线 | 1（分解）+ N 个 Agent × 各自 ReAct + 1（汇总）≈ **4~12 次** |

**只要其中一次撞上 429 或 5xx，那一步就降级** —— 这正是你看到的「三个 Agent 的 AI 合成环节**均**不可用」：
不是三个工具同时坏，而是三个 Agent 各发了一次请求、各自踩到了同一个限流窗口。
这类失败**退避重试一两次基本都能过**；不重试等于把「服务端瞬时抖动」翻译成「功能坏了」。

**修法**：新增 `fetchWithRetry()`，边界写清楚：

- 只重试 **429 与 5xx** 与**网络异常**（fetch reject）；
- 400 / 401 / 403 / 404 / 413 / 422 是**确定性**错误，**不重试**（重试只会让用户白等）；
- 最多 3 次尝试（首次 + 2 次退避），指数退避 + 抖动，上限 4s；**服务端给了 `Retry-After` 就听服务端的**；
- **用户取消（abort）绝不重试**；退避等待本身也是可中断的（否则「取消」要等好几轮退避才生效）；
- 重试耗尽后，错误信息**如实写明「已自动重试 N 次」**——用户据此能区分「服务端就是不行」和「刚才只是抖动」。

### R2：`llm.js` 里有个局部变量叫 `t`，**遮蔽了 i18n 的 `t()`**（本轮实测踩到）

`const t = await res.text()` 存响应文本，而同一个 `if (!res.ok)` 块里 new 了一行 `t('agent.llm.retried', …)`
→ 运行时抛 **`t is not a function`**，导致「重试耗尽后的错误信息」整段构造失败。
编译器和静态检查都不会报它，只有执行到那一行才炸。（这正是本项目模板闸门一直在防的
「`t` 被遮蔽」类缺陷，只是这次发生在脚本里。）

**修法**：`t` → `bodyText`；并顺手清掉 `src/agent/**` 里所有把 `t` 当形参/局部变量的写法
（`orchestrator.js` 3 处、`tools/index.js` 7 处），**新增 `t` 遮蔽闸门**：
凡从 i18n 引入 `t` 的文件，不得再用 `t` 作局部变量/形参（含检测器自检，防闸门本身失效）。

> 顺带说明：全仓扫描发现 `src/views/*`、`App.vue` 等 **18 处**历史上也把 `t` 用作局部变量，
> 经逐处核对**当前都不是活雷**（同作用域内没有 `t('key')` 调用，只在事件回调里当临时变量）。
> 未做批量改名——那是 13 个视图文件的纯改名 churn，与并行会话冲突成本高于收益；
> 本轮先把**AI 层**（出问题的这一层）钉死，视图层留作已知债务。

### R3（上一轮已修，这里记一笔）：失败原因曾被一律写成「网络或服务异常」

`isNetworkError()` 对 `aborted` 明确返回 false（刻意设计），于是超时/限流/密钥失效全被归成「网络问题」，
用户只能反复重试同一件错事。现已按 error.code + HTTP status 给出精确原因。

## 三、还有哪些失败**不归代码管**（如实说明）

修完之后仍然可能失败的，是这几类，各自有对应的自救动作：

| 剩余原因 | 特征 | 你该做什么 |
| --- | --- | --- |
| 服务端持续故障 / 额度用尽 | 重试 2 次后仍失败，文案写明状态码与「已自动重试 2 次」 | 换模型、查额度；别反复点重试 |
| 429 限流（免费/低价档常见） | 文案含「429」 | 隔一分钟再问；或把长问题拆开（每次问话的调用次数会显著下降） |
| 用户自己的密钥/模型名写错 | 文案含 401/404 | 去「AI 设置」改配置 |
| 卡片里的图**原件已被删** | 文案含「读取失败（图片可能已被删除或无法解析）」 | 重新上传/重发图片 —— 这与模型能力无关，任何 AI 都读不到 |
| 上下文确实过长（罕见，已有兜底） | 400 且提到 context length | 开新会话；或分批问 |

```
npm run build       → BUILD_EXIT=0 · check:build 52 分片就位
eslint / dep:check  → 通过 / 272 文件 0 环
i18n 三闸           → 通过（数据层 340 行、较基线新增 0；新文案已入字典 agent.llm.*）
```

新增 8 条闸门（`tests/agent-llm-resilience.test.mjs` 6 条 + `tests/vue-template-guard.test.mjs` 2 条）：

1. 429 → 退避重试并成功（断言确实请求了 3 次）；
2. 5xx 连续失败 → 重试到上限后抛出，且信息含「已自动重试 2 次」；
3. 400/401/404 → **只请求一次**（确定性错误不重试）；
4. 网络抖动（fetch reject）→ 重试后成功；
5. 用户取消 → **不再发请求**（不重试）；
6. 服务端给了 `Retry-After: 1` → 真的等满 1 秒再重试（不按自己的退避猛敲）；
7. `t` 遮蔽检测器自检：能抓 `const t =` / `(t) =>` / `catch (t)`，不误报 `task` / `txt`；
8. `src/agent` 下凡引入 i18n `t` 的文件不得把 `t` 用作局部变量/形参。
