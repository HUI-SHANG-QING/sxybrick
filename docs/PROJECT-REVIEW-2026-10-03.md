# SxyBrick 项目整体评估（2026-10-03）

> 评估方式：先采集客观数据（脚本统计 + git + 全仓扫描），**再下判断**；不凭印象。
> 所有数字可用文末的采集方式复现。

---

## 零、总体判断（先给结论）

**这是一个工程质量明显高于同类个人项目的作品，但存在两个结构性缺口。**

- **做得好的地方不是"功能多"，而是"有工程纪律"**：6 道自动门禁 + 1727 个测试用例 +
  22.8% 的注释密度 + 0 个循环依赖 + 0 个 `var` —— 这些是**很多商业项目都做不到**的。
- **两个结构性缺口**（按严重度）：
  1. **没有类型系统**，5.6 万行纯 JavaScript；
  2. **1727 个测试用例里没有一个是组件渲染测试** —— 78 个 Vue 组件的模板与响应式逻辑
     完全没有运行时验证，只靠 8 个需要真实浏览器的 smoke 脚本兜底。

## 二、分维度评价

### 2.1 工程基础设施 —— **强项（本项目最大的优势）**

6 道静态门禁 + 1727 个用例，且**全部挂在 `npm test` 上**（不是"跑一下看看"，
而是"不过就发不出去"）。更关键的是这些门禁**是演进而非堆砌**的：

- i18n 闸有**基线机制 + 净增护栏**（净增 > 0 拒绝自动认领，须显式 `--force-baseline`）——
  防止"一条命令把新增违规洗成存量"；
- 静默 catch 闸**只卡新增**，存量 49 处不阻塞、可渐进清理；
- SRS 不变量闸用**枚举式实测**（155 组边界输入）而非举例。

**判断**：这套门禁的**设计思路**（基线 + 只卡新增 + 护栏）比门禁本身更有价值，
它是可复制到任何项目的工程实践。

### 2.2 代码质量 —— **良好，有明显偏好**

- **注释密度 22.8%**，且注释写的是**"为什么"而非"是什么"**（例如
  `// round26 D4：移除 imageRefs 索引快速路径——该索引由 rebuildImageRefs 全量重建，
  但全仓除其自身外无任何调用方 → 一旦有人触发 rebuild，判定会用过期引用误删仍被引用的图片`）。
  这类注释在半年后能救回一次事故。
- 代码卫生近乎苛刻：`var` 0 处、`console.log` 3 处、`TODO` 0 处、循环依赖 0 个。
- **弱项**：`repo.js` 2885 行偏大，承担了过多职责（CRUD + 统计 + 回收站 + 同步相关）；
  `==` 77 处虽在可接受范围（1/724 行），但在有 `== null` 这类**有意使用**的背景下，
  缺类型系统时无法区分"故意"与"手滑"。

### 2.3 测试体系 —— **数量优秀，结构有缺口**

**优点**：1727 个用例 / 190 个文件，测试代码 26,228 行（占源码 21%）。
覆盖面很宽——数据层、SRS 算法、同步合并、墓碑、i18n、构建产物、门禁自身都被测到了。
更难得的是**大量"结构闸"**：把"某个 API 必须以某种形式被调用"写成测试
（如"绕过入口直接调算法函数必须被拦"、"视图层不得直写同步表"），这在个人项目里罕见。

**缺口（重要）**：

1. **零组件渲染测试**。78 个 `.vue` 组件的模板编译错误、响应式失效、
   computed/watch 时序问题，**只能靠 8 个需要真实浏览器的 smoke 脚本**发现，
   而 smoke 依赖 CDP、本地易跑 CI 未必跑。
2. **无覆盖率数据**。1727 个用例听起来多，但**从没测过"哪些代码一行没被执行过"**。
   5.6 万行代码 + 0 覆盖率报告，无法回答"核心路径是否都被测到了"。

### 2.4 架构与依赖 —— **良好**

- **0 个循环依赖**（且有门禁强制），依赖方向清晰（`views → repo → db`）。
- 模块职责基本清晰：`repo`（数据）、`agent/`（智能体）、`algorithms/`（算法）、
  `services/`（外部能力）、`utils/`（纯函数）、`composables/`、`views/`。
- **`repo.js` 是明显的单点过重**（2885 行），它同时管卡片 CRUD、统计、回收站、
  孤儿图清理、快照失效广播——是下一轮重构的首选目标。

### 2.5 数据层与同步 —— **项目中技术含量最高的部分**

这是我认为**最值得称赞**的模块：跨设备同步 + 字段级合并（`fieldTs`）+ 墓碑机制 +
LWW 仲裁 + 3 套合并策略（`idOnly` / `updatedAt` / `idOnly+isRecent`）。

它经得起 6 轮审计：最近三轮里**发现的 3 个真实缺陷全在同步层**
（批注墓碑漏写、孤儿图墓碑漏写、卡片级联失效），而且**都已被修掉并加了回归测试**。
能说明问题的地方在于：这些缺陷之所以能被发现，是因为**已有门禁把"该写墓碑却没写"变成了可检测项**。

### 2.6 算法正确性 —— **良好，且已被枚举式验证**

SM-2 / FSRS 双调度器、掌握度判定、遗忘预警、净值计算。
最近一轮用 **155 组边界输入的枚举实测**替代了此前的举例式验证，
发现并修掉了 `ease` 越界漂移与巩固状态脏值两个缺口。

**判断**：这个项目已经跨过了"算法靠直觉调参"的阶段，进入了"用不变量守住"的阶段——
这是算法类代码成熟度的标志。

### 2.7 安全 —— **良好**

- 所有 `v-html` 出口统一过 DOMPurify（`sanitize.js` 单点收口）；
- 用户可控内容（卡片正文、AI 回复、解析文本）默认净化，最近还补了**两层净化**（KaTeX 产物单独把关）；
- 注入用例 18/18 通过；
- 缺口：**没有 CSP**（`index.html` 未设），插件系统走 `Blob URL + 动态 import`
  （项目自己注释承认"本质上等同 eval"）。个人本地优先应用可接受，但**不应部署为多用户服务**。

### 2.8 国际化 —— **优秀**

8,795 行 / 46 文件的 zh-en 双语，且有**三道专门门禁**（视图反向扫描 + 数据层扫描 + 词条完整性）。
中文个人项目能把 i18n 做到这个程度并守住不变量，属于**少数派做法**。

### 2.9 产品完整度 —— **超出"个人项目"通常水平**

卡片 SRS、词库（单词/短语/句子/范文 + 词组）、资料库（含 OCR/多模态问答）、
知识图谱、思维导图、文档、番茄钟、计划、成就、统计、导出（PDF/Markdown/Anki/apkg/分享码）、
AI 助手（工具调用 + 结构化回复 + 检索）、跨设备同步、离线 PWA、演示模式。

**依赖只有 20 个运行时包**支撑以上功能，说明是**克制的技术选型**，不是靠堆库。

### 2.10 风险与技术债 —— **可控，但清单要管起来**

| 风险 | 严重度 | 说明 |
|---|---|---|
| **无类型系统** | 高（结构性） | 5.6 万行纯 JS，重构与并行协作的回归成本高；这正是"每轮修复都可能引出问题"的**底层原因之一** |
| **零组件渲染测试** | 中高 | 78 个组件的 UI 逻辑无运行时验证 |
| **无覆盖率数据** | 中 | 不知道哪些代码从未被执行 |
| 49 处完全空 catch | 中低 | 装门禁防新增；存量可渐进清理 |
| 145 处"catch 里只有注释" | 中低 | 比 49 处更值得复查：至少有注释说明，但仍是静默吞错 |
| `repo.js` 2885 行单点过重 | 中 | 重构首选目标 |
| 插件无沙箱 / 无 CSP | 低（本地应用） | 部署为多用户服务前必须解决 |
| **5 个提交未推送** | 低（流程） | 网络问题，但"本地领先远端 5 个提交"本身是协作风险 |

### 2.11 协作与流程 —— **好，但有隐患**

- git 纪律清晰（原子提交、显式文件列表、禁 `git add -A`）；
- 6 轮审计形成"改 → 审计兜底 → 装门禁 → 钉住回归"的闭环；
- **隐患**：并行会话共用一个工作区，**基线漂移**（我的 A/B 正则都被并行会话的改动放过）
  与**文件锁**（`EBUSY`、`git.exe` 被占用）都真实发生过；
  且当前**本地领先远端 5 个提交**，一旦出事回滚成本高。

## 三、优势总结（客观）

1. **门禁文化**——6 道门禁全部接入 `npm test`，且都有"只卡新增 + 基线 + 护栏"的设计自觉。
2. **测试投入**——1727 用例 / 26k 行测试代码，占源码 21%，覆盖到算法与结构层。
3. **注释质量**——22.8% 密度且解释"为什么"，是可复用的团队资产。
4. **技术选型克制**——20 个运行时依赖支撑完整功能面。
5. **同步/合并层的技术深度**——字段级合并 + 墓碑 + 多策略 LWW，经得起多轮审计。
6. **国际化完整度**——8.8k 行双语 + 三道门禁，中文项目里的少数派。
7. **闭环思维**——发现问题 → 修 → **加门禁让它不能再犯**，这一套已经跑通 4 次。

## 四、建议（按性价比排序）

| 优先级 | 措施 | 理由 |
|---|---|---|
| **1** | 给**核心组件**（`Review.vue` / `Cards.vue` / `Export.vue` / `FlipCard.vue`）补组件渲染测试 | 补上 78 个组件最大的验证缺口；比全面铺开便宜得多，收益最大 |
| **2** | 生成**覆盖率报告**（c8 / node --experimental-test-coverage） | 先知道"哪些代码从未被执行"，再决定补哪些测试——盲目补测试是浪费 |
| **3** | 逐步引入 **JSDoc 类型标注**（不是全面 TS 迁移） | 短期收益（编辑器提示、发现类型错误）成本低，可逐文件推进；避免"大爆炸迁移" |
| **4** | 拆分 `repo.js`（按域：`cards` / `stats` / `trash` / `images`） | 降低单点过重与并行冲突 |
| **5** | 清理 145 处"只有注释的 catch" | 逐个补 `console.debug` 或真实处理；比 49 处真空更值得查 |
| **6** | 推动**推送**并建立"本地不领先远端"的习惯 | 5 个提交的领先是实打实的协作风险 |
| **7** | `graphAuto.js` 补一行注释说明"此处刻意用更低门槛" | 成本≈0，能防未来审计者误"修"引入回归 |

## 五、评估的诚实边界

- 代码质量结论基于**静态扫描 + 测试结果 + 代码抽样阅读**，**没有**逐行审完 5.6 万行。
- **没有跑覆盖率**，因此"1727 个用例"只能说明测试**多**，不能说明测试**充分**。
- 组件层的评估基于"测试文件是否 import/mount 组件"，**未实际运行**应用验证 UI 行为。
- 同步层的多设备并发场景**未做真实多 tab 压测**（沙箱限制）。
- 性能评价主要来自 round124/127 的专项实测（导出预览 6.4×、写库 +33µs），
  **没有**全面的性能基线。
