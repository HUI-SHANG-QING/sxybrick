# round73 深度修复：「AI 有时候能回复、有时候回不了」的真因

> 触发问题（用户原话）：
> 「为什么有些是 agent 回复能成功，有些时候又不能，我明明已经设置成了最大输出长度（Token）65536」
> 「它连卡片内容都看不到？？？？你在修复个什么东西，不会其他模块的内容 AI 也看不到吧」

本轮不猜、不试：全部结论都用**代码事实 + 可执行闸门**钉住。

---

## 一、根因（3 条，都有证据）

### R1. 全链路非流式 + 硬编码 60s「总时长」超时 ← 「时好时坏」的主因

证据：`grep -rn "stream:\s*true|onToken|timeoutMs" src` 在设计上支持流式，但**没有任何调用方传过**
`stream: true`（唯一命中是 `llm.js` 内部的 `decoder.decode(value, { stream: true })`）。
于是 `src/agent/llm.js` 的 `timeoutMs ?? 60000` 在语义上等于：

> **「整段回答必须在 60 秒内写完并返回」，否则整个请求作废。**

60s 内模型实际能写多少？按 20–40 token/s 折算约 **1500–2000 汉字**。
所以失败不是随机的，而是**可算的**：

| 场景 | 结论 |
| --- | --- |
| 「你好」「什么是滑动窗口」 | 秒回 → 成功 |
| 「把 17 张卡逐张列出来」/「完整知识图谱」 | 长回答 → **必撞 60s** → 失败 |

用户看到的「有时候能、有时候不能」，本质是「**这轮要写多长**」的确定性函数。

### R2. `max_tokens` 调大与 60s 总超时**互相矛盾** ← 用户操作放大了故障

用户在「AI 设置 → 最大输出长度」选了 **65536**（≈4.7 万汉字）。
但 60s 内物理上写不出 4.7 万字（需要 ~1300 token/s）。
于是：**用户越把输出上限调大，模型越倾向于写长 → 越容易撞 60s 超时**。
旧默认 8192 时表现为「截断」（有续写兜底）；调到 65536 后表现变成「超时」——**同一个病，换了张脸**。

### R3. 超时被归类成「网络或服务异常」，且**已生成的内容被整段丢弃**

- `utils/offlineAI.js` 的 `isNetworkError()` 对 `aborted === true` **明确返回 false**（刻意设计：超时不该走离线兜底）；
  所以 TIMEOUT 会冒泡到 `agents/base.js` 的 catch，走 `buildLocalAnswer()` —— 这正是用户看到的那句
  「**AI 合成回答暂不可用（网络或服务异常）。以下是你本地数据的直接结果**」。
- 但原因根本没说对：密钥过期、429 限流、模型不存在、回答超长，**全都写「网络或服务异常」**。
  用户只能反复重试同一件错事（明明是密钥失效，却在重启路由器）。
- 更糟：非流式下 `abort` 时一个字都没拿到，**用户白等 60s 后什么都没得到**，重试还是同一结果。

### R4（附带发现）：「AI 连卡片内容都看不到」的**直接原因**是工具只回正面

`src/agent/tools/index.js` 的 `search_cards` 返回项是：

```js
{ id, subject, front: front.slice(0, 80), hasImage, tags, level }   // ← 没有 back
```

`get_weak_cards` 同样只有 `front`。
所以用户问「这张卡背面写了什么」时，**模型手上根本没有背面数据**，只能如实回答「我看不到背面」
——用户视角就是「AI 瞎了」。而工具描述里只强调了 `hasImage`，没告诉模型「要看背面请调 get_card_detail」。

同时 `agent/tools/compact.js` 默认 `maxItems = 8`：17 张卡的检索结果**只喂给模型前 8 张**
（虽有「还有 N 项」提示，但列表工具连 `offset` 参数都没有，模型想翻页也翻不了）。

## 二、修复

| # | 文件 | 改动 |
| --- | --- | --- |
| 1 | `src/agent/llm.js` | 流式时超时语义改为**空闲超时**（默认 120s，每收到增量重置计时器）；非流式保持 60s 总时长（回归安全） |
| 2 | `src/agent/llm.js` | 超时/取消时**抢救已生成内容**（返回部分 + 「因超时中断」标注），不再整段丢弃 |
| 3 | `src/agent/llm.js` | 流式分支兜底「服务端忽略 stream、直接回整段 JSON」的响应（`rawTail` + `tryParseLLMJson`） |
| 4 | `src/agent/orchestrator.js`、`pipeline.js` | Agent / 流水线链路**默认 `stream: true`**（调用方可覆盖） |
| 5 | `src/agent/agents/base.js` | 新增 `explainLlmFailure()`：按 error.code / HTTP status 给出**真实原因**（超时/限流/密钥/模型不存在/5xx），随 `buildLocalAnswer` 显示；`parseFinal` 容忍被砍断的 `<final>`（剥标签） |
| 6 | `src/agent/local-answer.js` + `src/i18n` | 降级文案支持 `{reason}` 插值，新增 9 条原因文案（zh/en 同步） |
| 7 | `src/agent/tools/compact.js` | `maxItems 8→20`、`maxChars 4000→6000`（17 张卡的正+背面摘要约 4600 字，现在能完整进上下文）；超预算时**按条数递减**并保持**合法 JSON**（旧实现会 `slice` 出半个 JSON，模型解析不了、还看不出缺了哪几条） |
| 8 | `src/agent/tools/index.js` | `search_cards` 返回 **`back` 摘要** + `limit`/`offset`/`hasMore` 翻页；`get_weak_cards` 补 `id` + `back`；两者描述明确写出「完整正文要调 `get_card_detail(id)`」 |
| 9 | `src/ai.js`、`src/views/AIAssistant.vue` | （上一轮被中断的收尾）对话入口改用 `buildFullContext(query)`：带 **RAG 原文片段**，而不是只有统计面板 |
| 10 | `scripts/check-view-i18n.mjs` | 第三道闸豁免 `toolRegistry.register` 的**元数据段**：`description`/`parameters` 是发给模型的 prompt 契约（中文、永不翻译），不是 UI 文案 |

### 关于第 10 条的取舍

这些说明文字的句长普遍很短（`'number: 本次返回条数，默认 20，最大 50'` 最长连续中文仅 6 字），
过不了「最长连续中文 > 24 字即视为 prompt」那条既有去噪规则 → **每次扩写工具说明都假红**，
逼人反复重锚基线，基线的意义被稀释成「点一下就好」，真正的 UI 泄漏反而更容易溜过。
现按**结构**精确挖空：只到第一个 `execute` 为止，工具**实现体**里的中文仍受闸门管辖。
基线因此瘦身 **94 条**（93 条工具说明 + 1 条已改走 `t()` 的 llm.js 文案），**零新增**。

## 三、验证

```
npm test            → 1203 passed / 0 failed   （基线 1191 + 本轮新增 12）
npm run build       → BUILD_EXIT=0
npm run check:build → ✓ 52 个词库分片全部就位
dep:check           → 272 个源文件，0 循环依赖
i18n --strict / --js→ 通过（数据层 440→341 行，较基线新增 0）
```

新增闸门 `tests/agent-llm-resilience.test.mjs`（12 条），钉住的行为契约：

1. 流式：5 片 × 40ms = 200ms 总时长 > 120ms 超时，**但每次间隔 < 超时 → 必须成功**（长回答不再被误杀）；
2. 流式：真卡死（无新数据超时）仍抛 `TIMEOUT`（不会永久挂起）；
3. 流式：中途超时 → 交出「前半段正文」+ 超时标注（不再白等一分钟一个字都没有）；
4. 非流式：超时仍抛 `TIMEOUT`（既有语义回归保护）；
5. 流式：服务端回非 SSE 整段 JSON → 兜底解析出正文；
6. 降级文案带 `reason` 时写「API 密钥无效或无权限」且**不再出现「网络或服务异常」**；
7. `parseFinal` 剥掉被砍断的 `<final>` 标签；工具调用不被当成最终回答；
8. `compact`：17 张卡（正+背面）在预算内**原样进上下文**，无省略提示；
9. `compact`：超预算时**仍是合法 JSON**（`JSON.parse` 通过）+ 保留顶层 `total` + 末尾「还有 N 项」；
10. `compact`：25 条小结果默认完整保留（默认 20 条上限生效）；
11. `search_cards`：25 张卡 → 第 1 页 20 条 + `hasMore:true`，第 2 页 5 条 + `hasMore:false`，两页**无重复无遗漏**，每项都带 `back`；
12. `get_weak_cards`：返回 `id` + `back`。

## 四、用户可感知的变化

- 长回答（逐张列卡片 / 完整图谱 / 长解析）**不再因为 60s 总时长被误杀**；真的卡死才中断。
- 万一还是中断 → **拿到已经生成的部分**，而不是一句「AI 合成回答暂不可用」。
- 失败时**明确告诉你是什么原因**：密钥无效 / 被限流 / 模型不存在 / 超时 —— 各自对应不同的自救动作。
- 「把 17 张卡列出来」这类需求，模型**确实拿到了全部 17 张（含背面摘要）**，并能翻页取更多。
- 问「这张卡背面写了什么」时，模型**手上有背面数据**，不再回答「我看不到」。

## 五、仍未做（按价值排序）

1. **max_tokens 与模型实际上限的对齐**：当前只有「服务端拒绝 max_tokens → 降级到 2000 重试一次」。
   若服务端因上下文超长拒绝（错误文本不含 max_tokens），仍会直接失败。建议按输入 token 估算做**自适应上限**。
2. UI 尚未展示「本次回答被截断/抢救」的独立提示位（目前混在正文末尾）。
3. `get_card_detail` 之外，资料库 / 笔记 / 计划等模块的列表工具同样缺 `back`/`offset` —— 需逐个补（本轮先修卡片域）。
4. 流式已具备，但 UI 仍无**打字机效果**（`onToken` 已通，只是没人消费）——属体验优化，非缺陷。
